# AAR: 작업 회고

미 육군의 After Action Review를 에이전트의 작업 세션에 적용한다. 같은 네 질문을 묻고, 답에서 교훈을 뽑고, 그 교훈이 다음 세션에 실제로 읽히게 만든다.

회고의 가치는 기록이 아니라 **다음 세션의 행동이 바뀌는 것**이다. 교훈이 막연하거나, 고칠 파일이 정해지지 않았거나, 고친 파일을 다음 세션이 읽지 않으면 회고는 아무것도 바꾸지 못한다. 셋 중 하나라도 빠지면 학습하는 것처럼 보이기만 하는 기록이 쌓인다. 이 스킬의 규칙은 전부 이 세 지점을 막기 위한 것이다.

## 네 질문

방금 끝난 작업이나 세션에 대해 순서대로 답한다. 짧게, 에이전트 자신의 말로, 사람 탓 없이 쓴다.

1. **무엇을 기대했나**: 계획, 지시, 예상 결과.
2. **실제로 무엇이 일어났나**: 실제 결과. 부분 완료, 에러, 조용히 실패한 것, 우회한 것을 포함한다.
3. **왜 달랐나**: 실제 메커니즘. "API가 배치 쓰기를 100건으로 자르고 부분 성공에도 200을 돌려준다"는 원인이다. "더 꼼꼼했어야 했다"는 원인이 아니다.
4. **다음엔 무엇을 하나**: 차이를 막았을 구체 규칙, 또는 잘 됐으니 반복할 방식.

계획대로 잘 끝난 작업도 회고 대상이다. 그때는 무엇이 잘 됐는지를 교훈으로 남긴다. 나쁜 날의 회고는 버그를 잡고, 좋은 날의 회고는 아직 드러나지 않은 좋은 패턴을 고정한다.

### 근거를 모은다

기억이 아니라 기록으로 답한다. 대화에서 실패한 도구 호출과 에러 문자열, 사용자가 정정한 지점, `git log`와 `git diff`, 테스트 출력을 본다. `humanism_talk` 의 `brief` 가 켜져 있었다면 마무리 블록의 "가설 X, 실제 Y"가 둘째, 셋째 질문의 1차 근거다.

근거로 확인한 것과 추정한 것을 구분한다. 셋째 질문에 확인된 메커니즘이 없으면 "원인 미확인"이라 쓰고, 확인 방법을 넷째 질문에 둔다. 그럴듯한 원인을 지어내면 틀린 교훈이 다음 세션에 고정된다.

## 교훈 뽑기

넷째 질문의 답에서 교훈을 0개에서 3개 뽑는다. 검증할 수 있는 교훈이 없으면 0개도 맞는 결과다. 억지로 만들지 않는다.

모든 교훈은 이 질문을 통과해야 한다: **6개월 뒤 다른 에이전트가 이 한 줄만 읽고, 판단 없이 무엇을 할지 알 수 있는가.**

통과하는 예:
- "배치 쓰기는 100건 단위로 자르고, 상태 코드가 아니라 반환된 행 수로 성공을 확인한다."
- "이 저장소의 테스트는 `uv run pytest`로 돌린다. 시스템 `pytest`는 의존성을 못 찾는다."
- "`brief.md`는 훅이 매 세션 통째로 주입하므로, 긴 표는 별도 참조 파일로 분리한다."

통과하지 못하는 예: "코드를 더 잘 쓴다", "API를 조심한다", "끝내기 전에 한 번 더 확인한다".

특정 도구, 명령, 숫자, 파일, 조건이 들어 있지 않으면 아직 교훈이 아니다. 구체화하거나 버린다.

## 수정 계획

교훈마다 하나를 묻는다: **다음 세션이 읽는 무언가가 바뀌지 않으면 같은 실수를 반복하는가.**

- **아니다**: 맥락으로만 남긴다. "이 벤더 API는 월요일에 느리다, 버그가 아니다" 같은 것. 메모리에 기록하고 끝낸다.
- **그렇다**: 수정 계획을 쓴다.

### 저장 위치를 고른다

교훈이 적용되는 범위로 고른다. 별도의 LESSONS 파일은 만들지 않는다. 다음 세션이 자동으로 읽는 곳에 넣어야 고리가 닫힌다.

| 범위 | 대상 |
|---|---|
| 이 프로젝트의 규칙 | 프로젝트 `CLAUDE.md` |
| 특정 스킬의 절차 | 그 스킬의 `SKILL.md` 또는 참조 파일 (수정은 `common` 스킬 규약을 따른다) |
| 사용자의 작업 방식, 선호, 맥락 | Claude Code 메모리 디렉토리 (경로는 세션 시스템 프롬프트에 있다) |
| 모든 프로젝트 공통 규칙 | `~/.claude/CLAUDE.md` |

### 계획을 쓴다

대상 파일과 넣을 문장을 정확히 쓴다. 교훈과 같은 기준이다. "배포 절차 개선"은 계획이 아니다. "`CLAUDE.md`의 배포 절에 '배포 후 건드린 서비스마다 실행 중인 버전을 조회해 빌드 해시와 비교한다' 추가"가 계획이다.

```
수정 계획
- 대상: CLAUDE.md, "배포" 절
  추가: "배포 스크립트의 종료 코드만 믿지 않는다. 배포 후 건드린 서비스마다
  실행 중인 버전을 조회해 빌드 해시와 비교한다."
- 대상: 메모리, feedback 유형
  추가: "사용자는 PR 본문에 파일 목록 나열을 원하지 않는다. 변경 이유와 결과만 쓴다."
```

### 중복을 먼저 본다

쓰기 전에 대상 파일과 메모리 디렉토리에서 같은 내용을 찾는다. 이미 있으면 새로 쓰지 않고 기존 항목을 고친다. 같은 교훈이 다른 문장으로 두 번 쌓이면 다음 세션이 어느 쪽을 따를지 헷갈린다.

기존 규칙이 이번 교훈과 충돌하면, 이번 근거가 기존 규칙을 뒤엎을 만한지 판단하고 그 판단을 계획에 적는다. 조용히 덮어쓰지 않는다.

### 승인받고 적용한다

계획은 AskUserQuestion으로 승인받는다. 항목별로 적용, 수정 후 적용, 건너뛰기를 고르게 한다. 사용자가 이번 요청에서 이미 "적용해", "고쳐", "apply", "fix it"이라고 했으면 바로 적용하고 무엇을 바꿨는지 보고한다.

사용자가 계획에 아무 답도 하지 않으면 승인이 아니다. 파일을 건드리지 않는다.

적용한 뒤에는 각 파일에 실제로 들어갔는지 확인한다. 스킬 파일을 고쳤으면 README 카탈로그도 맞는지 본다.

## 출력 형식

```
## 회고: <작업 이름>

**기대**: <한두 줄>
**실제**: <한두 줄. 부분 완료와 우회 포함>
**차이의 원인**: <메커니즘. 확인/추정 구분>
**다음**: <유지할 것, 바꿀 것>

### 교훈
- <검증 가능한 한 줄> (반영: <대상> / 맥락만)

### 수정 계획
<위 형식. 없으면 "없음">
```

그다음 AskUserQuestion으로 승인을 묻는다. 적용이 끝나면 바꾼 파일 경로와 상태(적용, 건너뜀)를 보고한다.

## 지키는 것

- 사람을 탓하지 않는다. 사용자의 지시가 원인이었어도 "지시가 모호했다"가 아니라 "X가 정해지지 않은 채 Y를 가정하고 진행했다"로 쓴다. 다음에 무엇을 확인할지가 교훈이다.
- 잘 된 회고만 반복되면 회고가 일하지 않는 것이다. 대부분 성공한 작업에서도 실제 마찰 지점을 찾는다.
- 교훈이 맥락뿐인데 수정 계획을 억지로 만들지 않는다. 규칙 파일이 잡음으로 차면 진짜 규칙이 묻힌다.
- 이 스킬은 다음 세션이 읽는 파일을 바꿀 뿐, 모델 자체를 바꾸지 않는다. 효과는 반영한 파일이 다음 세션에 로드된 뒤부터 난다. 결과를 보고할 때 이 이상을 주장하지 않는다.
