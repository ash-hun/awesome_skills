# refactor 모드: 서비스 리팩토링과 변경 문서

`dev_principle` 스킬의 참조 문서. `/dev_principle refactor [설계문서 경로]` 로 들어온다. 사용자가 이미 만들어진 서비스를 리팩토링해 달라고 할 때도 이 모드로 진행한다.

리팩토링은 동작을 그대로 두고 구조만 바꾸는 일이다. 그래서 실패하는 방식도 정해져 있다. 구조를 바꾸다가 동작이 같이 바뀌거나, 무엇을 왜 바꿨는지 기록이 남지 않아서 다음 사람이 diff 를 통째로 다시 읽어야 한다. 이 모드는 그 둘을 막는다. 동작은 테스트로 고정하고, 변경은 문서로 남긴다.

결과물은 항상 셋이다. 하나라도 빠지면 끝난 게 아니다.

- 리팩토링된 코드와 규칙에 맞게 옮긴 테스트
- 최신화한 서비스 문서: `docs/features.md`, `docs/api_spec.md`, 화면이 있으면 `docs/view_spec.md`
- 변경 문서: `docs/refactoring/YYYY-MM-DD-<서비스명>.md`

## 입력

- **설계문서**: `refactor` 뒤에 경로가 들어왔을 때만 설계문서가 있다고 본다. 인자가 없으면 저장소를 뒤져서 찾지 않고 곧바로 기본 방안으로 간다. 우연히 발견한 문서를 설계문서로 오인하면 사용자가 의도하지 않은 방향으로 코드 전체가 바뀐다.
- **대상 서비스**: 사용자가 지정한 경로, 지정이 없으면 현재 작업 디렉토리. 한 저장소에 서비스가 여럿이라 대상이 갈리면 묻는다.

인자로 받은 경로에 파일이 없으면 기본 방안으로 조용히 넘어가지 않는다. 경로가 틀렸다고 알리고 멈춘다.

## 무엇이 무엇을 정하는가

| 문서 | 정하는 것 | 언제 읽나 |
|---|---|---|
| 설계문서 또는 `references/default-plan.md` | 무엇을 어떤 구조로 바꿀지 | 설계문서가 있으면 설계문서, 없으면 기본 방안 |
| `references/code-rules.md` | 바꾼 코드가 어떤 모양이어야 하는지 | 항상 |
| `references/testing.md` | 테스트의 종류, 이름, mock, 분량 | 항상 |
| `references/docs.md` | 서비스 문서 3종 | 항상 |
| `references/logging.md`, `references/agent.md` | 로거, 에이전트 | 해당 코드가 있을 때 |

타입 힌트, docstring, OpenAPI 설명, 로거를 structlog 로 옮기는 일은 비즈니스 동작을 바꾸지 않으므로 리팩토링 범위 안이다.

## 설계문서와 코드 규칙이 부딪힐 때

설계문서의 지시와 코드 규칙이 서로 다른 결과를 요구하면 어느 쪽도 임의로 고르지 않는다. AskUserQuestion 으로 묻는다.

질문은 **위에서 아래로** 설명한다. 하위 모듈의 세부만 던지면 사용자는 그 모듈이 전체에서 어디에 있고 왜 문제가 되는지부터 스스로 복원해야 한다.

1. 프로젝트: 이 서비스가 무엇을 하는 서비스인지 한 문장
2. 구조: 전체 층 구조에서 지금 다루는 부분이 어디인지
3. 모듈: 그 모듈이 그 층에서 맡은 역할과 누가 부르는지
4. 충돌: 설계문서가 요구하는 것과 코드 규칙이 요구하는 것, 둘이 왜 함께 성립하지 않는지
5. 영향: 각 선택이 다른 모듈과 테스트에 미치는 차이

예:

> 이 서비스는 마크다운 게시글을 읽어 블로그 API 로 내보낸다. 구조는 api, service, repository 세 층이고, 지금 다루는 것은 repository 층의 `post_repository` 다. 이 모듈은 `post_service` 가 부르며 게시글 조회와 저장을 맡는다. 설계문서 3.2 절은 저장소마다 `AbstractRepository` 를 상속하라고 하고, 코드 규칙은 추상 클래스를 쓰지 않게 한다. 설계문서를 따르면 저장소 클래스 4개가 추상 메서드 6개를 구현하고, 코드 규칙을 따르면 공통 조회와 저장을 가진 구체 클래스 `BaseRepository` 하나를 상속한다.

선택지는 **설계문서대로** / **코드 규칙대로** 를 기본으로 두고, 각 선택지의 설명에 그 결과를 한 줄로 적는다. 충돌이 여러 건이면 한 번에 모아 묻는다. 이 모드에서 무엇을 묻든(계획 승인, 의도를 읽을 수 없는 테스트, 계획 이탈) 같은 순서로 위에서 내려오며 설명한다. 사용자의 결정은 변경 문서의 비고에 적는다.

## 흐름

`SKILL.md` 의 진행 순서(기획, 아키텍처, 하위 모듈)를 리팩토링에 맞춘 것이다. 승인과 테스트 고정은 코드 수정보다 앞에 온다.

1. **방향 확정**: 설계문서가 있으면 읽고, 없으면 `references/default-plan.md` 를 읽는다.
2. **as-is 분석과 기능 정의**: 대상 서비스의 구조와 기존 테스트를 읽고, 현재 서비스가 가진 기능 목록을 `features.md` 형식으로 정리한다. 기획 단계에 해당하며 승인받는다.
3. **계획 수립과 승인**: 목표 구조와 모듈별 변경 계획을 보여주고 승인받는다. 아키텍처 단계에 해당한다.
4. **동작 고정**: 기존 테스트와 mypy 를 돌려 기준선을 잡고, 테스트가 없는 기능은 특성 테스트를 먼저 쓴다.
5. **리팩토링**: 모듈 단위로 고치고, 단위마다 테스트를 돌린다.
6. **검증**: 전체 테스트와 mypy 를 돌려 기준선과 비교하고, 크리티컬 포인트를 점검한다.
7. **문서**: 서비스 문서 3종을 최신화하고 변경 문서를 쓴다.

2와 3은 하나의 AskUserQuestion 에 묶어 승인받아도 된다. 기능 목록이 바뀌지 않는 리팩토링에서는 기능 정의가 확인 성격이기 때문이다. 기능 목록 자체에 사용자 판단이 필요한 지점(죽은 기능, 둘로 갈라진 같은 기능)이 있으면 따로 묻는다.

### 방향 확정

설계문서가 있으면 그 문서가 구조의 기준이다. 기본 방안을 섞지 않는다. 설계문서가 다루지 않는 모듈은 건드리지 않고, 설계문서 내용이 현재 코드와 맞지 않으면 추측으로 메우지 않고 계획 단계에서 그 지점을 짚어 묻는다.

설계문서가 없으면 기본 방안을 쓴다. 기본 방안은 점검 목록이지 전부 적용하라는 명령이 아니다. 현재 코드에서 실제로 문제가 관찰되는 항목만 계획에 올린다.

### as-is 분석과 기능 정의

코드를 고치기 전에 아래를 파악한다. 이 내용이 계획과 변경 문서의 "리팩토링 전" 서술의 근거가 된다.

- 서비스 기능 목록과 기능별 진입점. 이것이 `features.md` 의 기능 ID 가 되고 테스트 파일명의 `{기능명}` 이 된다
- 모듈 목록과 각 모듈의 책임, 각 모듈이 어느 기능에 속하는지
- 모듈 간 호출 계층과 의존 방향. 역방향 import 와 순환 import 가 있는 곳
- 상태가 저장되는 곳 (DB, 파일, 프로세스 메모리, 외부 서비스)
- 외부 API 연동 지점. 테스트에서 mock 으로 바꿀 경계가 된다
- 설정과 비밀값이 들어오는 경로, 하드코딩된 비밀값
- 여러 곳에 중복된 코드와 로깅 방식
- 패키지 관리 도구, 테스트 실행 방법, 정적 검사 설정

### 기존 테스트 분석

기존 테스트를 무시하지 않는다. 기존 테스트는 원작성자가 "이 동작은 깨지면 안 된다"고 적어 둔 요구사항이다. 테스트를 하나씩 읽고 **의도**를 파악한다. 단언문이 무엇을 비교하는지가 아니라 그 테스트가 무엇을 보장하려는지를 읽는다.

분석 결과를 계획에 표로 넣는다.

| 테스트 | 의도 | 기능 | 옮겨 갈 위치 |
|---|---|---|---|
| `test_draft_not_listed` | 비공개 글이 목록 API 에 노출되지 않음을 보장 | `post_list` | `tests/integ/test_post_list.py` |

- 테스트를 옮기거나 고치더라도 의도는 남아야 한다.
- 이상해 보이는 단언(빈 문자열을 돌려주길 기대함 등)도 요구사항으로 취급한다. 고치지 않는다.
- 의도를 읽을 수 없는 테스트는 추측으로 분류하지 않고 계획 단계에서 묻는다.
- 테스트를 지우지 않는다. 대상 코드가 사라져 의미가 없어진 테스트는 계획에 표시해 승인받은 뒤에 지우고 비고에 적는다.
- 기존 테스트가 실제 외부 API 를 호출하면 mock 으로 바꾸는 것을 계획에 넣는다. 의도는 그대로 두고 경계만 바꾼다.
- 테스트 분량이 `references/testing.md` 기준보다 훨씬 많으면, 같은 의도를 중복으로 보장하는 테스트를 `parametrize` 로 합치는 계획을 올린다. 의도가 사라지는 삭제는 하지 않는다.
- 기존 테스트가 다루지 않는 기능을 함께 적는다. 그곳이 특성 테스트를 쓸 자리다.

### 계획 수립과 승인

계획은 위에서 아래로 쓴다. 서비스 전체의 현재 구조와 목표 구조를 먼저 보여주고 모듈별 내용으로 내려간다. 모듈별로 "지금 어떤 구조인지, 무엇으로 바꿀지, 왜 바꾸는지"를 적는다. 손대지 않을 모듈도 이유와 함께 적는다. 계획에 함께 넣는 것:

- 리팩토링 후의 디렉토리 트리. 호출 계층과 모듈명이 여기서 정해진다
- 기능별 atomic 모듈과 파이프라인 매핑. `features.md` 의 구현 파일 표 초안이다
- 기존 테스트 분석 표와 새로 써야 하는 테스트의 범위
- 패키지 관리 도구를 uv 로, 로거를 structlog 로 옮기는지 여부
- 발견한 보안 문제. 고치면 동작이 바뀌는 것은 따로 표시한다
- 설계문서와 코드 규칙이 부딪히는 지점. 계획 승인과 별개로 먼저 묻고 답을 계획에 반영한다

그다음 AskUserQuestion 으로 승인을 받는다. 선택지는 **계획대로 실행** / **수정 후 실행** / **중단**. 승인 전에는 서비스 코드를 고치지 않는다.

실행 중에 승인받은 계획에서 벗어나야 할 일이 생기면 작은 조정은 진행하고 변경 문서의 비고에 적는다. 모듈을 추가로 건드리거나 공개 인터페이스가 바뀌는 수준이면 다시 승인받는다.

### 동작 고정

기존 테스트가 있으면 먼저 `uv run pytest` 로 돌려 결과를 기준선으로 기록한다. 리팩토링 전부터 실패하던 테스트는 그대로 기록한다. `uv run mypy` 도 한 번 돌려 오류 수를 기록한다. 프로젝트가 아직 uv 를 쓰지 않으면 기존 방식으로 기준선을 먼저 잡고 나서 uv 로 옮긴다. 도구를 옮기다 깨진 것과 원래 깨져 있던 것을 구분하기 위해서다.

테스트가 없는 기능은 리팩토링 전에 특성 테스트를 쓴다. 특성 테스트는 올바른 동작이 아니라 **현재 동작**을 고정한다. 현재 코드가 이상한 값을 돌려주더라도 그 값을 그대로 단언한다.

- 기능의 진입점에서 쓴다. 내부 구현에 붙이면 리팩토링할 때 테스트도 같이 깨져서 증명이 안 된다. 그래서 특성 테스트는 대부분 `tests/integ/test_{기능명}.py` 가 된다.
- 외부 API 는 처음부터 mock 으로 둔다.
- 리팩토링 전 코드에서 통과하는 걸 확인하고 나서 다음 단계로 간다.
- 외부 의존 때문에 진입점에서 테스트를 쓸 수 없는 기능은 억지로 쓰지 않고 비고에 "미검증"으로 적는다.

단위 테스트(`tests/unit/test_{기능명}_{모듈명}.py`)는 모듈을 리팩토링하는 같은 단위 안에서 쓰고 통과시킨 뒤 다음 모듈로 간다. 나중에 몰아서 쓰지 않는다.

### 리팩토링

- 모듈 단위로 고치고, 한 단위가 끝날 때마다 테스트를 돌린다.
- 동작을 바꾸지 않는다. 공개 API 의 경로, 요청과 응답 형태, DB 스키마, 설정 키 이름은 설계문서나 승인된 계획이 명시적으로 바꾸라고 한 경우에만 바꾼다.
- 작업 중 버그나 보안 문제를 발견해도 리팩토링과 섞어 고치지 않는다. 동작이 바뀌면 전후 비교가 무의미해진다. 발견한 것은 비고에 적어 사용자가 따로 판단하게 한다. 비밀값 노출처럼 시급한 보안 문제는 마지막 보고 맨 위에 올린다.
- 손대는 모듈마다 코드 규칙을 적용한다. 구조만 옮기고 타입 힌트와 docstring 을 나중으로 미루지 않는다.
- 포맷과 들여쓰기는 기존 코드를 따른다. 모듈명, import 순서, 타입 힌트, docstring 은 기존 코드에 없더라도 코드 규칙을 따른다.

### 검증

- `uv run pytest tests/unit` 과 `uv run pytest tests/integ`: 둘 다 통과해야 한다. 기준선에서 통과하던 테스트가 실패하면 리팩토링이 동작을 바꾼 것이니 코드를 고친다. 테스트를 고쳐서 통과시키지 않는다. 테스트 수정이 정당한 경우는 테스트가 내부 구현(옮겨진 import 경로 등)에 묶여 있을 때뿐이고, 그렇게 고친 테스트는 의도가 보존됐는지 확인한 뒤 비고에 적는다.
- `uv run mypy`: 리팩토링한 모듈에서 오류 0.
- 의존 방향: 아래 층에서 위 층을 import 하는 줄이 없는지 grep 으로 확인한다.
- 기존 테스트의 의도: 분석 표의 테스트마다 같은 보장을 하는 테스트가 남아 있는지 대조한다.
- 크리티컬 포인트 네 가지(API 부하, 자원 점유, 보안, 구조 효율)를 리팩토링 전후로 비교한다.

돌려본 것만 확인했다고 쓴다. 실행하지 못한 검증은 못 했다고 쓴다.

## 변경 문서

리팩토링이 끝나면 반드시 쓴다.

- **위치**: 대상 서비스의 `docs/refactoring/YYYY-MM-DD-<서비스명>.md`. 같은 날 같은 서비스를 다시 리팩토링하면 그 파일을 갱신한다.
- **구조**: `assets/change-doc-template.md` 를 그대로 따른다. 아래 세 절의 제목과 순서를 바꾸지 않는다.

```markdown
## 1. 개요
## 2. 리팩토링 내용
## 3. 비고 및 특이사항
```

**개요**에는 날짜, 작성자, 대상 서비스, 기준(설계문서 경로 또는 "기본 방안"), 기준 커밋, 검증 결과 요약을 적는다. 작성자는 `git config user.name`, 기준 커밋은 리팩토링 시작 시점의 `git rev-parse --short HEAD`. git 저장소가 아니면 "없음". 검증 결과에는 pytest(unit, integ 각각)와 mypy 의 전후 수치, 크리티컬 포인트 점검 결과를 적는다.

**리팩토링 내용**은 모듈마다 문단을 나누고, 문단마다 리팩토링 전과 후를 나란히 쓴다. 독자는 diff 를 보지 않고 이 문서만 읽는다고 가정한다.

- 전과 후는 구조를 서술한다. 코드를 줄 단위로 풀어 쓰지 않는다.
- 변경 이유를 한두 문장으로 적는다. 설계문서 기반이면 해당 항목을 가리킨다.
- 파일이 옮겨지거나 이름이 바뀌었으면 옛 경로와 새 경로를 적는다.
- 테스트도 모듈로 다룬다. 기존 테스트가 어디로 갔는지, 무엇을 새로 썼는지 문단 하나로.
- 모든 모듈에 똑같이 적용한 변경(타입 힌트, docstring, structlog 로거, OpenAPI 설명)은 "공통 적용" 문단 하나에 모은다.
- 손대지 않은 모듈은 문단을 만들지 않는다.

**비고 및 특이사항**에는 아래를 적는다. 해당 사항이 없으면 "없음".

- 승인된 계획에서 벗어난 지점과 이유
- 테스트를 못 써서 검증하지 못한 기능
- 발견했지만 고치지 않은 버그, 보안 문제, 타입 불일치
- 내부 구현에 묶여 있어서 수정한 테스트
- 설계문서 지시 중 수행하지 못한 항목
- 설계문서와 코드 규칙이 부딪힌 지점과 사용자의 결정
- 배포할 때 사람이 해야 하는 일 (환경변수 추가, `LOG_FORMAT=json` 설정, 마이그레이션 실행, uv 전환에 따른 설치 명령 변경 등)

## 끝내기 전에

- 변경 문서가 `docs/refactoring/` 에 있고, 모듈 문단이 실제로 고친 모듈과 일치하는가
- `features.md`, `api_spec.md`, `view_spec.md`(화면이 있으면)가 리팩토링 후 구조와 맞는가
- `uv run pytest` 와 `uv run mypy` 를 마지막 수정 이후에 돌렸는가
- 테스트가 `tests/unit/test_{기능명}_{모듈명}.py`, `tests/integ/test_{기능명}.py` 규칙을 따르고, 외부 API 가 전부 mock 이고, 기존 테스트의 의도가 전부 남아 있는가
- import 경로만 읽고 각 모듈의 역할을 알 수 있는가. 역방향 import 가 없는가
- 손댄 모든 `.py` 에 모듈 docstring, 타입 힌트, 규칙대로의 import 순서가 있는가
- 로거가 `common/logger.py` 하나에서만 설정되는가
- `ABC` 로 만든 추상 클래스가 승인 없이 들어가 있지 않은가
- 엔드포인트마다 기능 설명, 인자 설명, 사용 예제가 있는가
- 미검증 기능과 발견한 버그, 보안 문제가 비고에 적혀 있는가

마지막 보고는 짧게 한다. 변경 문서 경로, 테스트와 mypy 결과(기준선 대비), 크리티컬 포인트 요약, 사용자가 결정해야 할 비고 항목.

## 범위 밖

- 새 기능 추가와 버그 수정. 동작이 바뀌는 작업은 리팩토링이 아니다. 개발 모드로 따로 한다.
- 서비스를 처음부터 새로 만드는 일.
- 프레임워크, 언어, DB 종류 교체. 단, 에이전트를 LangGraph 로 옮기는 일은 설계문서나 사용자가 요청하면 이 모드에서 한다.
- 커밋과 푸시. 사용자가 요청하면 그때 한다.
