# 서비스 문서 3종

`dev_principle` 스킬의 참조 문서. 문서를 처음 만들거나 갱신할 때, `/dev_principle docs` 로 들어올 때 읽는다.

서비스는 `docs/` 아래에 세 문서를 가진다. 이 셋 외의 상시 문서는 만들지 않는다. 문서를 잘게 쪼개면 어디에 무엇이 있는지가 또 하나의 지식이 되고, 그 지식은 아무 데도 적혀 있지 않다. 파일이 커지면 안에서 목차로 나눈다.

| 파일 | 무엇을 적나 | 언제 있나 | 템플릿 |
|---|---|---|---|
| `docs/features.md` | 서비스 기능, 기능별 세부 구현 파일과 테스트의 매칭 | 항상 | `assets/features-template.md` |
| `docs/api_spec.md` | 백엔드가 노출하는 모든 엔드포인트 | API 가 있으면 | `assets/api_spec-template.md` |
| `docs/view_spec.md` | 화면과 화면 안의 기능 | 화면이 있을 때만 | `assets/view_spec-template.md` |

refactor 모드가 남기는 `docs/refactoring/YYYY-MM-DD-<서비스명>.md` 는 상시 문서가 아니라 작업 기록이다.

예전 이름(`docs/api-spec.md`, `docs/screen-spec.md`)이 있으면 새 이름으로 옮기고 그 경로를 가리키는 링크를 고친다.

## 핵심 규칙: 문서는 코드에서 유도한다

이 문서들은 손으로 관리하는 산문이 아니라 코드의 투영이다. 라우터, 컴포넌트, 모듈을 읽고 거기 있는 사실을 옮긴다. 코드에 없는 것을 문서에 쓰지 않고, 코드에 있는데 문서에 없으면 그건 누락이다. 그래서 다시 만들어도 같은 결과가 나와야 한다.

- 생성 시각, 작성자, 빌드 번호를 넣지 않는다. 재생성할 때마다 diff 가 생기면 아무도 재생성하지 않고, 문서는 그날부터 낡는다.
- `Last Updated` 는 날짜만 적고, 문서 내용이 실제로 바뀐 날에만 갱신한다.
- 항목은 코드에 나타나는 순서가 아니라 정해진 키의 알파벳순으로 적는다. 기능은 기능 ID, 엔드포인트와 화면은 경로. 파일을 재배치했을 뿐인데 문서 diff 가 생기면 안 된다.
- 빈칸을 두지 않는다. 해당 없으면 "없음", 아직 없으면 "미구현"이라 쓴다. 빈칸은 "아직 안 썼다"와 "해당 없다"를 구분하지 못한다.

## 언제 갱신하나

작업을 할 때마다 그 작업 안에서 갱신한다. 나중으로 미루면 안 한다.

| 이번 작업에서 | 갱신할 문서 |
|---|---|
| 기능을 추가, 변경, 삭제 | `features.md` |
| 모듈을 추가, 이동, 이름 변경, 삭제 | `features.md` 의 구현 파일 표 |
| 테스트 파일을 추가, 이동 | `features.md` 의 테스트 칸 |
| 엔드포인트를 추가, 변경, 삭제 | `api_spec.md`, `features.md` 의 진입점 칸 |
| 화면을 추가, 변경, 삭제 | `view_spec.md`, `features.md` 의 진입점 칸 |

진행 순서의 1단계(기획과 기능 정의)에서 `features.md` 초안을, 2단계(아키텍처 설계)에서 모듈 매핑과 `api_spec.md` 의 엔드포인트 목록 초안을 만든다. 3단계 구현이 끝나면 초안을 실제 코드에 맞춘다. 계획과 코드가 다르면 코드가 맞고 문서를 고친다.

## docs/features.md

서비스가 무엇을 하는지와, 그 기능이 어느 파일에 구현되어 있는지를 잇는 문서다. 새로 온 사람이 기능 이름 하나로 코드와 테스트를 찾을 수 있어야 한다.

```markdown
# {서비스명} 기능 정의서

| 항목 | 값 |
| Last Updated | YYYY-MM-DD |

## 서비스 개요
## 기능 목록
| 기능 ID | 기능 | 진입점 | 상태 |
## 기능별 상세
### {기능 ID}: {기능 이름}
**설명**
**입력과 결과**
**처리 흐름**
**구현 파일**
| 파일 | 층 | 역할 |
**테스트**
| 종류 | 파일 |
**제약과 미구현**
## 공통 모듈
| 파일 | 역할 | 쓰는 기능 |
```

- **기능 ID** 는 snake_case 낱말이다(`post_publish`, `summary`). 테스트 파일명 `test_{기능명}_...` 의 `{기능명}` 과 같다. 한번 정하면 바꾸지 않는다. 바꾸면 테스트 파일명도 같이 바꾼다.
- **진입점** 은 사용자가 그 기능을 쓰는 입구다. `POST /posts`, `/posts/new` 화면, `uv run python -m app.batch.reindex`.
- **처리 흐름** 은 atomic 모듈이 파이프라인으로 이어지는 순서를 한 줄로 쓴다. `post_router` 에서 `post_service.publish` 로, `slug_builder`, `post_repository.upsert` 순.
- **구현 파일** 은 이 기능을 위해 존재하는 파일을 전부 적는다. 여러 기능이 함께 쓰는 파일은 공통 모듈 표에 적고 기능별 표에는 넣지 않는다.
- **테스트** 는 단위 테스트와 통합 테스트 파일을 적는다. 통합 테스트가 없으면 "없음"이라 쓰고 그 이유를 쓴다. 그 줄이 할 일 목록이 된다.

## docs/api_spec.md

`assets/api_spec-template.md` 를 그대로 뼈대로 쓴다.

- 제목은 `{서비스명} API 명세`. 문서가 저장소 밖으로 나가면 어느 서비스 것인지가 사라진다.
- 세부 API 명세의 소항목(Endpoint, 호출 규약, Request Body, Query/Path 파라미터, Response Body, 응답 코드, 호출 예시, 특이사항)은 하나도 빼지 않는다. 해당 없으면 "없음".
- **특이사항에는 반드시 재호출하면 어떻게 되는지를 쓴다.** GET 이면 "상태를 바꾸지 않음", 멱등한 POST 면 "같은 결과, 상태 변화 없음", 멱등하지 않으면 왜 그런지와 무엇을 조심해야 하는지. 호출하는 쪽이 재시도해도 되는지를 매번 코드를 읽어 판단하면 언젠가 틀린다.
- 인증 방식과 권한 요구를 엔드포인트마다 적는다. 공개 엔드포인트도 "없음(공개)"이라고 적는다.
- 호출 예시는 실제로 실행한 것을 쓴다. 성공 예시와 대표 실패 예시(검증 오류 등)를 하나씩. 예시에 실제 토큰이나 개인정보를 넣지 않는다.
- 목차는 세부 API 까지 링크한다.
- FastAPI OpenAPI 설명(`summary`, `description`, `Field`)과 내용이 어긋나지 않게 한다. 둘이 다르면 코드가 맞고 문서를 고친다.

## docs/view_spec.md

화면이 있는 서비스에만 만든다. 백엔드만 있는 서비스에는 만들지 않는다. `assets/view_spec-template.md` 를 채운다.

- 제목은 `{서비스명} 화면 기능 정의서`.
- 화면 목록은 경로 알파벳순. 상태는 구현됨 / 미구현.
- 화면마다 목적, 레이아웃, 데이터(어느 API 에서 무엇을), 상태와 파라미터, 인터랙션, 빈 상태, 에러 상태.
- **빈 상태와 에러 상태를 반드시 적는다.** 코드에 그 분기가 없으면 "처리 없음"이라고 적는다.
- 사용자 입력을 그대로 렌더링하는 곳(댓글, 이름, 마크다운 본문)은 인터랙션 칸에 이스케이프나 sanitizer 처리 여부를 적는다.
- 메뉴에 링크가 있는데 화면이 없으면 미구현 절에 적는다.

## 끝내기 전에

1. 새 기능과 새 모듈이 `features.md` 에 있고, 구현 파일과 테스트 칸이 실제 파일과 맞나?
2. 새 엔드포인트가 `api_spec.md` 에 있고 재호출 줄이 채워져 있나?
3. 새 화면이 `view_spec.md` 에 있고 빈 상태와 에러 상태가 적혀 있나?
4. 지운 것이 문서에서도 지워졌나?
5. 문서를 지금 다시 만들면 diff 가 없나?
