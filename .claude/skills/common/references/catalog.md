# 카탈로그 문서화

`common` 스킬의 참조 문서. 저장소의 README에서 스킬 카탈로그 구간을 다시 쓴다.

설치된 스킬을 실제로 읽고 README의 스킬 카탈로그를 다시 쓴다.

문서가 썩는 이유는 대개 **frontmatter의 `description`만 베껴 쓰기** 때문이다. 그건 모델이 스킬을 언제 켤지 판단하는 트리거 문구지, 사람이 "이게 뭘 하는 물건인가"를 이해하는 설명이 아니다. 사람에게 필요한 건 본문에 있다 — 사다리 7단계, 태그 체계, 출력 포맷, 하지 않는 일. **모든 SKILL.md는 본문까지 읽는다.**

## 1. 수집

저장소의 `.claude/skills/*/SKILL.md`를 전부 읽는다. 이 저장소가 전역 설치의 원본이므로 `~/.claude/skills` 아래 심볼릭 링크는 같은 파일을 가리킨다 — 따로 읽지 않는다. 각각에서:

- frontmatter: `name`, `description`, `argument-hint`, `disable-model-invocation`, `license`
- 본문: 실제 동작, 절차, 출력 형식, 명시적으로 범위 밖이라고 선언한 것
- 같은 디렉토리의 부속 파일(`scripts/`, `references/`, `assets/`) 유무 — 있으면 self-contained가 아니므로 기록

`disable-model-invocation: true`면 명시 호출 전용이다. 호출 방식 칸에 반영한다.

## 2. 출처와 라이선스 확인

추측하지 않는다. 잘못된 출처 표기는 빈칸보다 나쁘다. 순서대로:

1. 스킬 디렉토리의 `LICENSE`, frontmatter `license:`, 본문 안의 업스트림 URL
2. `.claude/settings.json`의 permissions allowlist에 남은 `curl` URL, `git log`
3. 후보 레포를 특정했다면 `curl -s "https://api.github.com/repos/<owner>/<repo>"`로 라이선스 확인
4. 그래도 모르면 표에 `-` 또는 `출처 미상`으로 두고, 마지막 보고에서 사용자에게 알린다

## 3. 설치 형태와 실제 동작의 간극 확인

이게 이 스킬이 존재하는 두 번째 이유다. 업스트림이 훅·플러그인·MCP 런타임과 함께 배포하는 스킬을 SKILL.md만 복사해 설치한 경우, 스킬 문서에 적힌 기능 일부가 이 프로젝트에서는 **동작하지 않는다** — 세션 자동 활성화, 환경변수/설정파일 기반 기본 모드, 상태줄, `/plugin` 자동 업데이트가 전형적이다.

본문에 그런 서술이 보이면 부속 파일이 실제로 설치됐는지 확인하고, 없으면 해당 스킬 항목에 경고 한 줄을 남긴다. 사용자가 문서대로 따라 했는데 안 되는 상황을 미리 막는 게 목적이다.

`.claude/settings.json`의 `enabledPlugins`/`extraKnownMarketplaces`로 활성화된 플러그인은 로컬 SKILL.md가 아니므로 카탈로그 표에 섞지 말고 구조 섹션에서 따로 언급한다.

## 4. README 갱신

기본 대상은 `./README.md`(인자로 다른 경로를 받으면 그쪽). 마커 사이만 교체한다:

```
<!-- skills:start -->
... 생성 구간 ...
<!-- skills:end -->
```

- **마커가 있으면** 그 사이만 교체한다. 바깥은 사람이 쓴 것으로 간주하고 손대지 않는다.
- **README는 있는데 마커가 없으면** — 기존 문서에 스킬 카탈로그로 보이는 구간이 있으면 그 구간을 마커로 감싸 교체할지 사용자에게 확인한다. 없으면 어디에 넣을지 묻는다. 임의로 덮어쓰지 않는다.
- **README가 없으면** 제목·한 줄 소개 + 마커 구간 + 라이선스/크레딧까지 갖춘 새 문서를 만든다.

문서 언어는 기존 README를 따른다. 새로 만드는 경우 프로젝트의 다른 문서와 대화 언어를 따른다.

## 5. 생성 구간의 구조

```markdown
## 설치된 스킬

| 스킬 | 호출 | 한 줄 요약 | 출처 |
|---|---|---|---|
| [`name`](.claude/skills/name/SKILL.md) | `/name [인자]` | ... | [repo](url) |

## 스킬 상세

### <계열 또는 주제 묶음>

#### `name`
본문에서 뽑은 실제 동작. 절차가 있으면 번호 목록, 출력 포맷이 정해져 있으면 그 형식,
범위 밖이라고 선언한 것, 비활성화 방법. 설치 형태 때문에 안 되는 기능이 있으면 ⚠️ 한 줄.

## 디렉토리 구조
(트리 + 플러그인 등 스킬 아닌 항목 각주)

## 스킬 추가하기
(설치 명령 + 확인 항목)

## 라이선스 / 크레딧
(출처별 묶음)
```

스킬이 3개 이하면 상세 섹션을 생략하고 표의 요약을 조금 길게 쓴다. 형식을 채우는 게 목적이 아니다.
계열이 뚜렷하면(`ponytail`, `ponytail-review`, `ponytail-audit`…) 묶어서 소제목을 준다 — 9개를 평평한 목록으로 늘어놓으면 관계가 안 보인다.

## 분량 감각

한 스킬당 상세는 2~6줄. 본문을 그대로 옮기면 README가 아니라 사본이 된다. 사용자가 알아야 하는 건 "이걸 언제 부르고, 부르면 뭐가 나오고, 뭘 안 해주는가"다. 링크가 있으니 나머지는 원문으로 보낸다.

## 마무리 보고

갱신 후 세 줄 이내로:

- 추가/삭제/변경된 스킬
- 출처나 라이선스를 확정 못 한 항목
- 설치 형태 때문에 경고를 붙인 항목

바뀐 게 없으면 그렇게 말하고 파일을 건드리지 않는다.
