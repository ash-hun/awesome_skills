# msg_check — 작업 메시지 검수

커밋, PR, 진행 보고는 코드보다 오래 남고 코드보다 많이 읽힌다. 6개월 뒤 `git log` 를 훑는 사람, 리뷰 큐에서 PR 을 고르는 사람, 슬랙에서 스크롤하며 상태를 확인하는 사람 — 모두 **맥락 없이, 빠르게** 읽는다. 이 스킬은 그 독자 입장에서 사용자가 쓴 메시지를 점검한다.

이 스킬은 **검수만** 한다. 사용자가 쓴 메시지가 입력이고, 지적 사항과 수정안이 출력이다. 원문의 내용을 새로 지어내지 않는다 — 수정안은 원문이 담은 사실을 더 잘 전달하도록 고치는 것이지, 없는 내용을 채우는 게 아니다. 거꾸로 원문에 있던 조건과 불확실성("권한을 받으면", "스테이징에서 미확인")도 지우지 않는다 — 조건을 뺀 수정안은 원문보다 강한 약속을 하게 된다.

## 흐름

1. **종류 판별** — 커밋 / PR / 진행 보고 중 무엇인지 정한다. 애매하면 형태로 판단한다(`type(scope):` 로 시작하면 커밋, `##` 섹션이 있으면 PR). 그래도 모르면 묻는다.
2. **종류별 규칙 읽기** — 해당 참조 문서 하나만 읽는다.
   - 커밋 → `references/commit.md`
   - PR → `references/pr.md`
   - 진행 보고 → `references/report.md`
3. **맥락 수집** — 지칭 표현을 판단하려면 메시지가 가리키는 대상을 알아야 한다. 커밋이면 `git diff --staged`, PR 이면 `git log <base>..HEAD` 와 `git diff <base>...HEAD --stat` 를 본다. 진행 보고처럼 저장소 밖 내용이면 대화 맥락으로 판단한다.
4. **네 기준으로 검수** — 아래 "검수 기준". 어색한 표현은 `references/korean-style.md` 의 목록과 대조한다.
5. **결과 출력** — 아래 "출력 형식".
6. **실행 확인** — 커밋·PR 이면 AskUserQuestion 으로 실행 여부를 묻고, 승인받으면 실행한다. 진행 보고는 실행할 게 없으므로 수정안을 내고 끝낸다.

## 검수 기준

네 가지다. 각 기준은 독자가 겪는 실패 하나씩에 대응한다.

### 1. 가시성 — 한눈에 읽히는가

독자는 메시지를 읽지 않고 훑는다. 핵심이 첫 줄에 있고, 구조가 눈에 보여야 한다.

- 첫 줄(커밋 제목, PR 제목, 보고 첫 문장)만 읽어도 무엇을 했는지 알 수 있는가
- 문단 덩어리 대신 섹션·불릿으로 나뉘어 있는가
- 한 불릿에 한 가지 사실만 있는가
- 같은 수준의 항목이 같은 형식으로 나열되는가(한 곳은 문장, 한 곳은 명사형이면 섞인 것)

### 2. 자연스러운 한국어 — 어색한 표현·번역투가 없는가

영어식 구문을 그대로 옮긴 문장은 읽는 속도를 떨어뜨린다. "~를 진행했습니다", "~에 대한 처리", "~되어지다" 같은 표현은 내용을 흐리게 만든다. `references/korean-style.md` 에 유형별 목록과 고친 예가 있다.

기술 용어는 번역하지 않는다. `middleware`, `retry`, `cache` 를 억지로 "중간 처리기", "재시도 로직"으로 바꾸는 건 개선이 아니다. 고치는 대상은 문장 구조지 용어가 아니다. 다만 "fix 했습니다", "refactoring 진행" 처럼 영어 동사를 한국어 어미에 붙인 혼용은 한국어 동사로 바꾼다.

### 3. 과잉 설명이 없는가 — 세 가지만 남긴다

작업 메시지에 들어갈 내용은 세 가지뿐이다.

- **작업한 문제 및 기능** — 무엇을, 왜
- **작업한 결과** — 무엇이 달라졌나
- **특이사항** — 독자가 알아야 할 예외, 주의점, 후속 작업 (없으면 생략)

이 셋에 속하지 않는 내용은 덜어낸다. 자주 끼어드는 것:

- 작업 과정·시행착오 서술("처음엔 A 로 했다가 안 돼서 B 로…")
- 코드를 줄 단위로 풀어 쓴 설명 — diff 가 이미 보여준다
- 누구나 아는 배경 설명
- 자기 평가("깔끔하게 정리했습니다", "완벽하게 해결")
- 같은 내용을 제목과 본문에서 반복

과정 중에 독자가 알아야 할 결정(왜 A 대신 B 를 택했나)이 있으면 그건 과정이 아니라 **특이사항**이다. 남긴다.

### 4. 지칭 표현 — 맥락 없는 독자도 가리키는 대상을 알아보는가

작성자는 머릿속 맥락으로 "그 버그", "해당 기능", "이 부분"을 쓰지만, 독자에게는 그 맥락이 없다. 전체 맥락(diff, 대화, 저장소 구조)을 보고, 가리키는 대상을 독자가 특정할 수 있는 이름으로 바꾼다.

- 대명사·지시어("이거", "그 부분", "해당 이슈", "위 문제") → 구체 이름(`AuthMiddleware`, `#142 로그인 만료 버그`)
- 작성자만 아는 별칭("새 버전", "옛날 방식", "우리가 얘기한 거") → 독자가 알아볼 이름
- 한 메시지 안에서 같은 대상을 다른 이름으로 부르는지("토큰 갱신"과 "리프레시"가 같은 것을 가리킴) → 하나로 통일
- 대상의 층위가 맞는지 — 파일 하나를 고쳤는데 "인증 시스템 개선"이라 부르면 과장, 모듈 전체를 바꿨는데 함수 이름 하나로 부르면 축소

맥락을 봐도 대상을 특정할 수 없으면 추측으로 이름을 넣지 않는다. 지적 사항에 "무엇을 가리키는지 확인 필요"로 남기고 사용자에게 묻는다.

## 출력 형식

항상 이 순서로 낸다.

```markdown
## 검수 결과

- **가시성**: 통과 | 수정 — <무엇이 문제인지 한 줄>
- **자연스러운 한국어**: 통과 | 수정 — <원문 표현 → 고친 표현>
- **과잉 설명**: 통과 | 수정 — <덜어낸 내용 한 줄 요약>
- **지칭 표현**: 통과 | 수정 | 확인 필요 — <원문 지칭 → 고친 지칭>

## 수정안

<바로 복사해 쓸 수 있는 최종 메시지. 커밋이면 코드 블록 안에>
```

- 네 기준이 모두 통과면 수정안 대신 "수정 없음"이라 쓰고 원문을 그대로 둔다. 통과한 메시지를 고치는 척하지 않는다.
- 수정 항목이 여러 개면 기준 아래에 중첩 불릿으로 늘어놓는다.
- "확인 필요"가 있으면 수정안에 `<?>` 로 자리만 표시하고, AskUserQuestion 으로 무엇을 가리키는지 묻는다.

## 실행

커밋·PR 은 검수 뒤 AskUserQuestion 으로 묻는다. 선택지는 **수정안으로 실행** / **원문 그대로 실행** / **실행 안 함**. 승인 없이 실행하지 않는다 — 커밋과 PR 은 남에게 보이는 기록이고 되돌리기 번거롭다.

- 커밋: `git diff --staged` 가 비어 있으면 실행하지 않고 알린다. 메시지는 heredoc 으로 넘긴다(`git commit -F - <<'EOF'`). 훅을 건너뛰는 `--no-verify` 는 쓰지 않는다.
- PR: 현재 브랜치가 원격에 없으면 push 도 필요하다는 걸 같이 묻는다. 본문은 `gh pr create --title "..." --body-file -` 로 넘긴다.
- 실행 후 결과(커밋 해시, PR URL)를 한 줄로 보고한다.

## 범위 밖

- 메시지 초안을 처음부터 쓰는 일. 원문이 없으면 "검수할 메시지를 붙여달라"고 요청한다.
- 코드 리뷰. diff 는 지칭 판단을 위한 맥락으로만 읽는다.
- 이슈, 릴리스 노트, CHANGELOG. 형태가 비슷해 보여도 독자와 규칙이 다르다.
