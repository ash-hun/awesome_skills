# PR 규칙

`msg_check` 의 참조 문서. 검수 대상이 PR 제목·본문일 때 읽는다.

---

## 독자

PR 의 첫 독자는 리뷰어다. 리뷰어는 본문을 읽고 (1) 무엇을 봐야 하는지, (2) 어디부터 봐야 하는지, (3) 어떻게 확인하면 되는지를 알고 싶어 한다. 두 번째 독자는 나중에 `git blame` 을 따라 들어온 사람이다 — 이 사람에게는 **왜**가 제일 중요하다.

## 제목

커밋 제목 규칙을 따른다: `<type>(<scope>): <한국어 요약>`, 명사형 종결, 마침표 없음. 여러 커밋을 묶는 PR 이면 가장 큰 변경을 대표로 쓴다. 스쿼시 머지하면 PR 제목이 그대로 커밋 제목이 되기 때문에 규칙을 맞춘다.

## 본문 구조

```markdown
## 작업 내용
- <작업한 문제 및 기능 — 무엇을, 왜>

## 결과
- <무엇이 달라졌나 — 동작, 수치, 화면>
- <확인 방법 — 리뷰어가 따라 할 수 있는 명령이나 절차>

## 특이사항
- <리뷰어가 알아야 할 예외, 의도적으로 하지 않은 것, 후속 작업>
```

- 섹션 이름은 이 셋으로 맞춘다. 저장소에 PR 템플릿(`.github/pull_request_template.md`)이 있으면 그 템플릿의 섹션을 우선하고, 세 요소가 템플릿의 어느 칸에 들어가는지만 본다.
- 특이사항이 없으면 섹션째 뺀다. "특이사항 없음"이라고 쓰지 않는다.
- 스크린샷·벤치마크 수치는 **결과**에 넣는다.
- 관련 이슈는 본문 끝에 `Closes #123`.

## PR 에서 특히 자주 보이는 문제

- **커밋 로그 나열** — 커밋 메시지를 그대로 불릿으로 붙인 본문. 리뷰어에게 필요한 건 변경의 요약이지 작업 순서가 아니다. 과잉 설명으로 지적하고 묶어서 요약한다.
- **파일 목록 나열** — "a.ts 수정, b.ts 수정, c.ts 추가". diff 탭이 이미 보여준다. 파일이 아니라 변경의 의미로 쓴다.
- **확인 방법 없음** — 결과에 "잘 동작함"만 있고 어떻게 확인했는지 없음. 가시성 문제로 지적하고, 사용자가 실제로 확인한 절차를 묻는다(지어내지 않는다).
- **범위 밖 변경 은폐** — diff 에는 무관한 포맷팅·리팩터링이 섞였는데 본문엔 언급이 없음. 지칭 표현 기준에서 "대상의 층위" 문제로 지적하고, 특이사항에 한 줄 넣도록 제안한다.

## 예시

원문:

```
## 변경사항
- 이것저것 수정
- 리팩토링 진행
- 테스트 추가

해당 기능에 대한 개선 작업을 진행하였으며 관련 테스트 또한 추가되어졌습니다.
```

수정안:

```markdown
## 작업 내용
- 주문 목록 API 가 페이지마다 사용자 정보를 N 번 조회하던 문제를 한 번의 조인 쿼리로 바꿈

## 결과
- `GET /orders?page=1` 응답 시간 820ms → 140ms (로컬, 주문 100건 기준)
- `pytest tests/api/test_orders.py` 로 페이지네이션 경계 테스트 3건 추가

## 특이사항
- `OrderSerializer` 필드 순서가 바뀌었지만 응답 JSON 키는 같음
```

(수치와 파일명은 원문과 diff 에 있는 것만 쓴다. 원문에 없으면 `<?>` 로 비워두고 묻는다.)
