## 개발 원칙: 멱등성

이 프로젝트는 **같은 작업을 두 번 해도 한 번 한 것과 결과가 같게** 만드는 것을 기본값으로 둔다.
이유는 복구 때문이다. 멱등하지 않으면 중간에 죽었을 때 복구가 "사람이 손으로 현재 상태 파악하기"가 되고, 멱등하면 "다시 실행"으로 끝난다.

**진행 방식:** 작업 중에 선택을 묻지 않는다. 갈리는 지점은 가장 그럴듯한 쪽을 골라 끝까지 가고, 판단과 근거는 끝에 모아 보고한다. 멈추고 확인받는 경우는 권한 변경·삭제·외부 배포처럼 되돌리기 어렵거나 위험한 실행뿐이다.

구현할 때 지키는 것:

1. **만들기 전에 필요한지 묻는다** — 존재하지 않는 코드가 가장 멱등하다. 이미 있는 걸 다시 짜면 정본이 둘이 되고, 둘은 갈라진다.
2. **무엇이 "같은 것"인지 먼저 정한다** — 재실행해도 변하지 않는 값(파일명, 외부 ID, 사람이 정한 코드)을 자연 키로 쓴다. 자동 증가 ID와 생성 시각은 후보가 아니다.
3. **상태를 만들지 말고 맞춘다** — `create_x()` 대신 `ensure_x()`, `IF NOT EXISTS`, upsert, `exist_ok=True`.
4. **어디서 죽어도 재실행이 답이 되게 한다** — 5단계 중 3단계에서 죽는 경우를 실제로 상상한다.
5. **확인과 변경 사이의 틈을 없앤다** — 코드의 중복 체크는 UX용이고, 실제 보증은 DB 유니크 제약이 한다. 둘 다 필요하다.
6. **결정과 부수효과를 한 함수에 섞지 않는다** — 계산은 순수하게, I/O는 경계에서. 그래야 "두 번 불러도 되나?"에 답할 수 있다.
7. **비결정적 값은 경계에서 만들어 주입한다** — `uuid4()`, `datetime.now()`, `random`을 로직 안에서 호출하지 않는다.

프로젝트 환경:

- 파이썬 의존성은 **uv** (`pyproject.toml` + 커밋된 `uv.lock`). `requirements.txt`를 만들지 않는다.
- 실행은 **Docker** (`docker compose up -d`). 이미지 태그에 `latest`를 쓰지 않고, 빌드는 `uv sync --frozen`.
- 명세 문서는 `docs/api-spec.md`(백엔드)와 `docs/screen-spec.md`(프론트) 두 개로 고정한다.
  엔드포인트·화면을 만들거나 고치면 그 작업 안에서 갱신한다. 작성 규칙은 `/develop_rule spec` 에 있다.
  문서에 생성 시각·버전 번호를 박지 않는다 — 재생성마다 diff가 생기면 아무도 재생성하지 않는다.

코드 스타일:

- 모듈은 **기능/목적 단위**로 나눈다(`order/`, `payment/`). 종류별(`services.py`, `utils.py`)로 나누지 않는다.
- `class`는 유지할 상태나 주입할 의존성이 있을 때만. 없으면 함수.
- 파이썬 파일 최상단 설명은 **한 줄**. 한 줄에 안 담기면 파일이 두 가지 일을 하고 있다는 신호다.
- import는 두 그룹 — 외부(표준+서드파티)를 줄 길이 오름차순, 한 줄 띄고, 로컬을 줄 길이 내림차순.
- 없어도 되는 import는 넣지 않는다 (`from __future__ import annotations` 등).
- 모듈 상수는 import 직후에 모아 선언한다. 기본값을 함수 안에 리터럴로 흩뿌리지 않는다.
- 주석은 **왜(why)만**. 설명이 코드보다 길면 설명을 지운다.
- 일부러 감수한 한계는 마커로 남긴다. 단순화는 `# ponytail: <한계>, <업그레이드 조건>`,
  의도적 비멱등은 `# idempotent: <이유>, <해결 방법>`. 둘 다 `/develop_rule debt` 가 장부로 모은다.

작업을 끝내기 전: **"이걸 지금 한 번 더 실행하면 어떻게 되나?"** 에 말로 답할 수 있어야 한다.
비자명한 셋업·동기화 로직에는 두 번 돌리는 체크를 하나 남긴다 (`./setup.sh && ./setup.sh`).
검증한 것과 검증하지 않은 것은 구분해서 보고한다.

자세한 층별 지침(셋업/코드/API)이 필요하면 `develop_rule` 스킬을 참조한다.
