# 명세 문서

`develop_rule` 스킬의 참조 문서. `/develop_rule spec` 으로 들어온다.

서비스마다 `docs/` 아래에 **두 개**를 만든다. 더 만들지 않는다.

| 파일 | 무엇을 적나 | 누가 읽나 |
|---|---|---|
| `docs/api-spec.md` | 백엔드가 노출하는 모든 엔드포인트 | API를 호출하는 쪽 — 프론트, 다른 서비스, 나중의 나 |
| `docs/screen-spec.md` | 프론트엔드 화면과 그 안의 기능 | 화면을 고치거나 이어받는 사람, 기획/QA |

두 개로 고정하는 이유가 있다. 문서를 잘게 쪼개면 어디에 무엇이 있는지가 또 하나의 지식이 되고, 그 지식은 아무 데도 안 적혀 있다. 파일이 커지면 안에서 목차로 나누되 파일을 늘리지 않는다.

---

## 핵심 규칙: 문서는 코드에서 유도한다

**이 문서들은 손으로 관리하는 산문이 아니라 코드의 투영이다.** 라우터·컴포넌트를 읽고 거기 있는 사실을 옮긴다. 코드에 없는 것을 문서에 쓰지 않고, 코드에 있는데 문서에 없으면 그건 누락이다.

그래서 **다시 만들어도 같은 결과가 나와야 한다.** 코드가 그대로인데 재생성했더니 diff가 생긴다면 문서에 코드와 무관한 것이 섞여 있다는 뜻이다.

지켜야 할 것:

- **생성 시각·작성자·빌드 번호를 박지 마라.** 재생성할 때마다 diff가 생기고, 그러면 아무도 재생성하지 않게 되고, 문서는 그날부터 낡는다.
- **`Last Updated`는 예외지만 규칙이 있다.** 날짜만 적고 시각은 적지 않는다. 그리고 **문서 내용이 실제로 바뀐 날**로만 갱신한다 — 코드가 그대로인데 문서를 다시 생성했다면 이 값도 그대로다. 이 구분을 지키면 "다시 만들어도 diff 없음"이 유지되고, 동시에 읽는 사람이 이 문서가 언제 기준인지 알 수 있다.
- **엔드포인트·화면은 코드에 나타나는 순서가 아니라 경로 알파벳순으로 적는다.** 코드 순서에 의존하면 파일을 재배치했을 뿐인데 문서 diff가 생긴다.
- **"현재 미구현"을 빈칸으로 두지 마라.** 없으면 없다고 적는다. 빈칸은 "아직 안 썼다"와 "해당 없다"를 구분하지 못한다.

## docs/api-spec.md

**제목은 항상 `{프로젝트 또는 서비스 명} API 명세`다.** 그냥 "API 명세"로 두지 않는다 — 문서가 저장소 밖으로 나가는 순간(슬랙, 위키, 첨부) 어느 서비스 것인지가 사라진다.

구조는 아래로 통일한다. `assets/api-spec-template.md`가 그대로 뼈대다.

```markdown
# {서비스명} API 명세

| 항목 | 값 |
| Last Updated | YYYY-MM-DD |
| Base URL | ... |

## 목차
## 개요
## 공통 규약
## 세부 API 명세
### METHOD /path
#### Endpoint
#### 호출 규약        method, header, 인증, Content-Type
#### Request Body
#### Response Body
#### 응답 코드
#### 호출 예시
#### 특이사항
## 데이터 모델
```

**세부 API 명세의 7개 소항목은 하나도 빼지 않는다.** 해당 없으면 "없음"이라고 적는다. 빈칸은 "아직 안 썼다"와 "해당 없다"를 구분하지 못하고, 읽는 사람은 그 차이 때문에 결국 코드를 열어본다.

**`특이사항`에는 반드시 "재호출하면 어떻게 되는가"를 포함한다.** 이게 이 문서에서 가장 값이 나가는 줄이다. 호출하는 쪽이 재시도해도 되는지를 매번 코드를 읽어 판단하고 있다면 그 판단은 언젠가 틀린다. GET이면 "상태를 바꾸지 않음", 멱등한 POST면 "같은 결과, 상태 변화 없음", 멱등하지 않으면 **왜 그런지와 무엇을 조심해야 하는지**를 적는다. 그 밖에 제약(rate limit, 크기 제한, 알려진 함정)도 여기 모은다.

**목차는 세부 API까지 링크한다.** 엔드포인트가 셋만 넘어가도 스크롤로 찾게 되는데, 그때부터 사람들은 문서 대신 코드를 열기 시작한다.

**호출 예시는 실제로 실행한 것을 쓴다.** 손으로 지어낸 예시는 필드명이 하나씩 틀리고, 그걸 믿고 붙인 클라이언트가 깨진다. 성공 예시 하나로 끝내지 말고 대표적인 실패(검증 오류 등)도 하나 넣는다 — 클라이언트가 실제로 다뤄야 하는 건 그쪽이다.

## docs/screen-spec.md

`assets/screen-spec-template.md`를 채운다.

```markdown
# 화면기능 명세

## 화면 목록
| 경로 | 화면 | 목적 | 상태 |
경로 알파벳순. 상태는 구현됨 / 미구현.

## 화면별 상세
### `/path` — 화면 이름
**목적** — 한 줄.
**레이아웃** — 위에서 아래로 어떤 블록이 오는지.
**데이터** — 어느 API에서 무엇을 받는지.
**상태·파라미터** — URL 쿼리, 클라이언트 상태.
**인터랙션** — 사용자가 뭘 하면 뭐가 일어나는지.
**빈 상태 / 에러 상태** — 데이터가 없을 때, API가 실패했을 때 무엇이 보이는지.

## 공통 컴포넌트
여러 화면이 공유하는 것. 어디에 있고 무엇을 받는지.

## 미구현 / 알려진 제약
지금 없는 것, 눌러도 안 되는 것. 링크는 있는데 페이지가 없으면 여기 적는다.
```

**빈 상태와 에러 상태를 반드시 적는다.** 대부분의 화면 문서가 "잘 됐을 때"만 그려놓고 끝나는데, 실제로 사람을 오래 붙잡는 건 목록이 0개일 때와 서버가 안 뜰 때다. 코드에 그 분기가 없으면 문서에 "처리 없음"이라고 적어라. 그 줄이 곧 할 일 목록이 된다.

**미구현을 숨기지 마라.** 메뉴에 링크가 있는데 페이지가 없으면 그건 사용자가 만나는 404다. 문서에 적혀 있으면 의도된 범위이고, 안 적혀 있으면 버그다.

## 언제 갱신하나

엔드포인트나 화면을 **추가·변경·삭제한 그 작업 안에서** 갱신한다. 나중으로 미루면 안 한다.

작업을 마치기 전에 확인해라:

1. 새로 만든 엔드포인트가 `api-spec.md`에 있나? `재호출` 줄이 채워져 있나?
2. 새로 만든 화면이 `screen-spec.md`에 있나? 빈 상태·에러 상태가 적혀 있나?
3. 지운 것이 문서에서도 지워졌나?
4. 문서를 지금 다시 만들면 diff가 없나? 있다면 시각·순서처럼 코드와 무관한 것이 섞여 있다.
