# 기본 리팩토링 방안

`refactoring_service` 스킬의 참조 문서. 설계문서 인자가 없을 때 읽는다.

기본 방안의 목표는 두 가지다.

- **영속성 있는 운영 구조**: 프로세스가 재시작되거나 다른 환경으로 옮겨져도 서비스가 같은 상태로 다시 뜬다.
- **확장성을 고려한 구조**: 기능이나 연동이 추가될 때 고쳐야 하는 곳이 한 군데로 모인다.

이 문서는 **무엇을 바꿀지**를 고르는 목록이다. 바꾼 코드의 모양(모듈명, 타입 힌트, 객체화, 테스트 구조, 도구)은 `references/code-rules.md` 가 정하고 그쪽은 항상 적용한다.

아래는 점검 목록이다. 항목마다 "이런 증상이 보이면 이렇게 바꾼다"로 적었다. 증상이 현재 코드에서 실제로 관찰되는 항목만 계획에 올린다. 증상이 없는데 구조를 미리 깔아두는 것은 리팩토링이 아니라 과잉설계다.

## 영속성 있는 운영 구조

### 상태가 프로세스 메모리에 있다

증상: 모듈 전역 딕셔너리나 리스트에 세션, 작업 큐, 캐시, 카운터를 보관한다. 재시작하면 사라지고 프로세스를 둘로 늘리면 서로 다른 값을 본다.

바꾸는 방향: 사라지면 안 되는 상태는 DB 나 영속 저장소로 옮긴다. 사라져도 되는 캐시는 그대로 두되 그 사실이 코드에서 드러나게 한다. 저장소가 이미 있으면 그걸 쓰고 새 인프라를 들이지 않는다. 새 저장소가 필요해지면 계획 단계에서 사용자에게 알린다.

### 파일을 컨테이너나 작업 디렉토리 안에 쓴다

증상: 업로드, 생성 파일, SQLite 파일을 코드 디렉토리 아래 상대 경로에 쓴다. 컨테이너를 다시 만들면 사라진다.

바꾸는 방향: 데이터 경로를 설정값 하나로 모으고, compose 나 배포 설정에서 그 경로를 볼륨에 연결한다.

### 설정과 비밀값이 코드에 박혀 있다

증상: 접속 주소, 포트, 키, 환경별 분기가 소스 여러 곳에 흩어져 있다.

바꾸는 방향: 설정을 읽는 모듈 하나로 모으고 환경변수에서 받는다. 필수 값이 없으면 기동 시점에 실패하게 한다. 기존 설정 키 이름과 기본값은 유지한다. 비밀값을 발견하면 저장소에서 지우는 것과 별개로, 이미 노출된 값이니 교체가 필요하다고 비고에 적는다.

### 스키마와 초기 데이터를 손으로 맞춘다

증상: 테이블 생성이 앱 기동 코드에 섞여 있거나, 문서에 적힌 SQL 을 사람이 실행해야 한다. 두 번 실행하면 오류가 난다.

바꾸는 방향: 스키마 변경을 마이그레이션으로 분리하고 앱 기동과 떼어낸다. 초기화와 시드는 두 번 실행해도 같은 상태가 되게 한다(`IF NOT EXISTS`, upsert). 프로젝트가 이미 쓰는 마이그레이션 도구가 있으면 그걸 따른다.

### 기동과 종료가 불안정하다

증상: 의존 서비스가 준비되기 전에 떠서 죽는다. 종료 신호를 받으면 처리 중이던 요청이나 작업이 버려진다. 살아 있는지 확인할 방법이 없다.

바꾸는 방향: 헬스체크 엔드포인트를 두고, 의존 서비스 대기를 compose 헬스체크 조건으로 건다. 종료 신호에서 진행 중인 작업을 마치고 연결을 닫는다.

헬스체크 엔드포인트 추가는 엄밀히는 새 동작이다. 계획에 명시하고 승인받은 경우에만 넣는다.

### 장애를 추적할 수 없다

증상: `print` 로 찍거나 예외를 삼킨다. 어떤 요청에서 무엇이 실패했는지 로그로 알 수 없다.

바꾸는 방향: 공통 모듈의 로거(`common/logger.py`) 하나로 통일하고 표준 출력으로 낸다. 예외를 삼키는 곳은 로그를 남기게 한다. 예외를 삼키던 곳에서 다시 던지도록 바꾸면 동작이 바뀌므로, 그건 하지 않고 비고에 적는다.

## 확장성을 고려한 구조

### 한 파일이 여러 책임을 진다

증상: 라우트 핸들러 안에 입력 검증, 업무 규칙, SQL, 외부 호출이 한꺼번에 들어 있다. 파일 하나가 계속 커진다.

바꾸는 방향: 세 층으로 나눈다.

- 진입 층: HTTP 나 CLI 요청을 받아 입력을 해석하고 응답 형태로 바꾼다.
- 업무 층: 규칙과 흐름. 프레임워크와 DB 드라이버를 직접 알지 못한다.
- 저장 층: DB 와 파일 접근.

의존은 진입 층에서 업무 층, 업무 층에서 저장 층으로만 흐른다. 층별 디렉토리 이름과 파일 이름 규칙은 `references/code-rules.md` 의 "호출 계층과 모듈명"을 따른다. 층을 나눌 만큼 코드가 없는 작은 모듈은 나누지 않는다.

### 같은 로직이 여러 곳에 복사되어 있다

증상: 같은 검증, 같은 쿼리, 같은 변환이 핸들러마다 조금씩 다르게 들어 있다.

바꾸는 방향: 한 곳으로 모은다. 복사본마다 동작이 미세하게 다르면 합치기 전에 그 차이가 의도인지 확인한다. 판단할 수 없으면 합치지 않고 비고에 적는다. 합치면서 한쪽 동작이 조용히 바뀌는 것이 가장 흔한 사고다.

### 외부 연동이 코드 곳곳에 퍼져 있다

증상: 외부 API 호출, 메일 발송, 결제 연동 코드가 업무 로직 사이사이에 직접 들어 있다. 연동 대상을 바꾸려면 여러 파일을 고쳐야 한다.

바꾸는 방향: 연동마다 클라이언트 클래스 하나로 모으고(`client/mail_client.py` 의 `MailClient`) 업무 층은 생성자로 주입받은 그 객체만 부른다. 추상 클래스를 먼저 세우지 않는다. 기능 이름을 가진 메서드(`send_welcome_mail`)가 있는 구체 클래스면 충분하다.

### 모듈이 서로를 양방향으로 참조한다

증상: 순환 import, 지연 import 로 순환을 피한 흔적, 한 모듈을 고치면 관계없어 보이는 모듈이 깨진다.

바꾸는 방향: 공통으로 쓰는 부분을 아래 층으로 내리거나 의존 방향을 한쪽으로 정한다.

### 구조가 기술 종류로만 나뉘어 있다

증상: `models/`, `utils/`, `helpers/` 에 모든 것이 섞여 있어서 기능 하나를 고치려면 디렉토리 전부를 돌아다녀야 한다.

바꾸는 방향: 기능이 여러 개이고 서로 독립적이면 도메인 단위로 묶는다. 기능이 하나뿐인 작은 서비스는 지금 구조를 유지한다.

### 프로세스를 늘릴 수 없다

증상: 로컬 파일 락, 메모리 세션, 프로세스 내 스케줄러 때문에 인스턴스를 둘 이상 띄우면 중복 실행이나 불일치가 난다.

바꾸는 방향: 상태를 프로세스 밖으로 빼서 프로세스를 무상태로 만든다. 주기 작업은 중복 실행되어도 결과가 같게 하거나 실행 주체를 하나로 분리한다.

## 하지 않는 것

- 몸통 없는 추상 클래스, 제품이 하나뿐인 팩토리, 바뀔 일이 없는 값의 설정화. 기능 관점의 추상화와 클래스로 묶는 것 자체는 적극적으로 한다. 줄이는 대상은 기능을 갖지 않는 뼈대다.
- 프레임워크, 언어, DB 종류 교체. 구조 리팩토링의 범위를 넘는다.
- 증상이 없는 항목의 적용. 계획에는 관찰된 증상과 그 위치(파일, 함수)를 근거로 적는다.
- 공개 API 형태와 DB 스키마 변경. 필요하다고 판단되면 계획에서 따로 표시해 승인받는다.
