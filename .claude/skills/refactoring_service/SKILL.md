# refactoring_service: 서비스 리팩토링과 변경 문서

리팩토링은 동작을 그대로 두고 구조만 바꾸는 일이다. 그래서 실패하는 방식도 정해져 있다. 구조를 바꾸다가 동작이 같이 바뀌거나, 무엇을 왜 바꿨는지 기록이 남지 않아서 다음 사람이 diff 를 통째로 다시 읽어야 한다. 이 스킬은 그 둘을 막는다. 동작은 테스트로 고정하고, 변경은 문서로 남긴다.

결과물은 항상 두 가지다. 하나라도 빠지면 끝난 게 아니다.

- 리팩토링된 코드
- 변경 문서 (`docs/refactoring/YYYY-MM-DD-<서비스명>.md`)

## 입력

- **설계문서**: 인자로 경로가 들어왔을 때만 설계문서가 있다고 본다. 인자가 없으면 저장소를 뒤져서 찾지 않고 곧바로 기본 방안으로 간다. 우연히 발견한 문서를 설계문서로 오인하면 사용자가 의도하지 않은 방향으로 코드 전체가 바뀐다.
- **대상 서비스**: 사용자가 지정한 경로, 지정이 없으면 현재 작업 디렉토리. 한 저장소에 서비스가 여럿이라 대상이 갈리면 묻는다.

인자로 받은 경로에 파일이 없으면 기본 방안으로 조용히 넘어가지 않는다. 경로가 틀렸다고 알리고 멈춘다.

## 무엇이 무엇을 정하는가

읽을 문서가 둘이고 역할이 다르다.

| 문서 | 정하는 것 | 언제 읽나 |
|---|---|---|
| 설계문서 또는 `references/default-plan.md` | 무엇을 어떤 구조로 바꿀지 | 설계문서가 있으면 설계문서, 없으면 기본 방안 |
| `references/code-rules.md` | 바꾼 코드가 어떤 모양이어야 하는지 | 항상 |

코드 규칙은 여덟 가지다. 상세와 예시는 `references/code-rules.md` 에 있고, 여기에는 무엇이 있는지만 적는다.

- **호출 계층과 모듈명**: 의존은 한 방향으로만 흐른다. import 경로만 읽고 그 모듈의 역할을 알 수 있어야 한다.
- **멱등성과 공통 모듈**: 모듈은 두 번 실행해도 같은 상태가 된다. 재사용되는 것은 공통 모듈로 모으고, logger 는 반드시 공통 모듈로 둔다.
- **타입 힌트**: 모든 함수의 인자와 반환값에 필수.
- **객체화와 상속**: 기능 관점의 추상화를 적극적으로 하고 상태와 의존은 클래스로 묶는다. 추상 클래스는 가급적 쓰지 않는다. 상속 깊이는 1에서 2를 권장한다.
- **파일 최상단 주석**: 모든 `.py` 파일 첫머리에, 전체 프로젝트 관점에서 이 모듈이 무엇인지 쓴다.
- **테스트**: `tests/unit/`(모듈별 단위 테스트)과 `tests/integ/`(API 수준 시나리오 e2e 테스트)로 나눠 쓰고 둘 다 통과시킨다. 기존 테스트는 의도를 분석해서 보존한다.
- **도구**: 테스트는 pytest, 정적 검사는 mypy, 패키지 관리는 uv.
- **OpenAPI 문서**: FastAPI 기준으로 엔드포인트마다 기능 설명, 인자 설명, 사용 예제를 넣되 과하게 쓰지 않는다.

타입 힌트, docstring, OpenAPI 설명을 붙이는 일은 동작을 바꾸지 않으므로 리팩토링 범위 안이다.

코드 규칙이 다루지 않는 판단은 `develop_rule` 스킬의 규칙을 기본으로 따른다. 둘이 부딪히면 코드 규칙이 우선한다. 특히 `develop_rule` 은 요청하지 않은 추상화를 만들지 않게 하지만, 이 스킬을 실행하는 동안에는 기능 관점의 추상화를 적극적으로 한다는 기준이 우선한다. Python 이 아닌 코드에는 호출 계층, 공통 모듈, 파일 최상단 주석의 세 원칙을 적용하고 나머지는 `develop_rule` 을 따른다.

## 설계문서와 코드 규칙이 부딪힐 때

설계문서의 지시와 코드 규칙이 서로 다른 결과를 요구하면 어느 쪽도 임의로 고르지 않는다. AskUserQuestion 으로 사용자에게 묻는다.

질문은 **위에서 아래로** 설명한다. 하위 모듈의 세부만 던지면 사용자는 그 모듈이 전체에서 어디에 있고 왜 문제가 되는지부터 스스로 복원해야 한다. 아래 순서로 맥락을 내려온 뒤에 선택지를 낸다.

1. 프로젝트: 이 서비스가 무엇을 하는 서비스인지 한 문장
2. 구조: 전체 층 구조에서 지금 다루는 부분이 어디인지
3. 모듈: 그 모듈이 그 층에서 맡은 역할과 누가 부르는지
4. 충돌: 설계문서가 요구하는 것과 코드 규칙이 요구하는 것, 둘이 왜 함께 성립하지 않는지
5. 영향: 각 선택이 다른 모듈과 테스트에 미치는 차이

예:

> 이 서비스는 마크다운 게시글을 읽어 블로그 API 로 내보낸다. 구조는 api, service, repository 세 층이고, 지금 다루는 것은 repository 층의 `post_repository` 다. 이 모듈은 `post_service` 가 부르며 게시글 조회와 저장을 맡는다. 설계문서 3.2 절은 저장소마다 `AbstractRepository` 를 상속하라고 하고, 코드 규칙은 추상 클래스를 쓰지 않게 한다. 설계문서를 따르면 저장소 클래스 4개가 추상 메서드 6개를 구현하고, 코드 규칙을 따르면 공통 조회와 저장을 가진 구체 클래스 `BaseRepository` 하나를 상속한다.

선택지는 **설계문서대로** / **코드 규칙대로** 를 기본으로 두고, 각 선택지의 설명에 그 결과를 한 줄로 적는다. 충돌이 여러 건이면 한 번에 모아 묻되 건마다 위 순서를 지킨다. 같은 층의 충돌은 프로젝트와 구조 설명을 한 번만 쓴다.

이 방식은 충돌 질문에만 쓰는 게 아니다. 이 스킬에서 사용자에게 무엇을 묻든(계획 승인, 의도를 읽을 수 없는 테스트, 계획 이탈) 같은 순서로 위에서 내려오며 설명한다.

사용자의 결정은 변경 문서의 비고에 적는다.

## 흐름

순서가 의미를 가진다. 특히 승인과 테스트 고정은 코드 수정보다 앞에 온다.

1. **방향 확정**: 설계문서가 있으면 읽고, 없으면 `references/default-plan.md` 를 읽는다. `references/code-rules.md` 는 항상 읽는다.
2. **as-is 분석**: 대상 서비스의 구조와 기존 테스트를 읽는다.
3. **계획 수립과 승인**: 모듈별 변경 계획을 보여주고 승인받는다.
4. **동작 고정**: 기존 테스트와 mypy 를 돌려 기준선을 잡고, 테스트가 없는 영역은 특성 테스트를 먼저 쓴다.
5. **리팩토링**: 모듈 단위로 고치고, 단위마다 테스트를 돌린다.
6. **검증**: 전체 테스트와 mypy 를 돌려 기준선과 비교한다.
7. **변경 문서 작성**: `assets/change-doc-template.md` 구조로 쓴다.

### 방향 확정

설계문서가 있으면 그 문서가 구조의 기준이다. 기본 방안을 섞지 않는다. 설계문서가 다루지 않는 모듈은 건드리지 않고, 설계문서 내용이 현재 코드와 맞지 않으면(이미 없는 모듈을 가리킴, 서로 모순되는 지시) 추측으로 메우지 않고 계획 단계에서 그 지점을 짚어 묻는다.

설계문서가 없으면 기본 방안을 쓴다. 기본 방안은 점검 목록이지 전부 적용하라는 명령이 아니다. 현재 코드에서 실제로 문제가 관찰되는 항목만 계획에 올린다.

### as-is 분석

코드를 고치기 전에 아래를 파악한다. 이 내용이 계획과 변경 문서의 "리팩토링 전" 서술의 근거가 된다.

- 모듈 목록과 각 모듈의 책임
- 진입점과 요청이 흐르는 경로
- 모듈 간 호출 계층과 의존 방향. 역방향 import 와 순환 import 가 있는 곳
- 상태가 저장되는 곳 (DB, 파일, 프로세스 메모리, 외부 서비스)
- 설정과 비밀값이 들어오는 경로
- 여러 곳에 중복된 코드와 로깅 방식
- 패키지 관리 도구, 테스트 실행 방법, 정적 검사 설정

**기존 테스트는 따로 세부 분석한다.** 테스트 코드를 하나씩 읽고 각 테스트가 무엇을 보장하려는지 의도를 파악한다. 단언문을 옮겨 적는 게 아니라 "이 테스트가 깨지면 어떤 요구사항이 깨진 것인가"를 읽는다. 기존 테스트는 원작성자가 남긴 요구사항이고, 리팩토링 중에 테스트를 옮기거나 고칠 때 이 의도가 기준이 된다. 분석 형식은 `references/code-rules.md` 의 "기존 테스트 분석".

### 계획 수립과 승인

모듈별로 "지금 어떤 구조인지, 무엇으로 바꿀지, 왜 바꾸는지"를 정리해 보여준다. 손대지 않을 모듈도 이유와 함께 적는다. 계획에 함께 넣는 것:

- 리팩토링 후의 디렉토리 트리. 호출 계층과 모듈명이 여기서 정해진다.
- 기존 테스트 분석 표와, 각 테스트가 `unit/` 과 `integ/` 중 어디로 가는지
- 새로 써야 하는 테스트의 범위
- 패키지 관리 도구를 uv 로 옮기는지 여부
- 설계문서와 코드 규칙이 부딪히는 지점. 이건 계획 승인과 별개로 먼저 묻고, 답을 계획에 반영한다

계획도 위에서 아래로 쓴다. 서비스 전체의 현재 구조와 목표 구조를 먼저 보여주고 나서 모듈별 내용으로 내려간다.

그 다음 AskUserQuestion 으로 승인을 받는다. 선택지는 **계획대로 실행** / **수정 후 실행** / **중단**.

승인 전에는 서비스 코드를 고치지 않는다. 서비스 전반의 구조를 바꾸는 작업은 되돌리는 비용이 크고, 방향이 틀린 걸 다 고친 뒤에 알게 되면 변경 문서까지 전부 버리게 된다.

실행 중에 승인받은 계획에서 벗어나야 할 일이 생기면(예상 못 한 의존, 계획한 분리가 불가능함) 작은 조정은 진행하고 변경 문서의 비고에 적는다. 모듈을 추가로 건드리거나 공개 인터페이스가 바뀌는 수준이면 다시 승인받는다.

### 동작 고정

기존 테스트가 있으면 먼저 `uv run pytest` 로 돌려 결과를 기준선으로 기록한다. 리팩토링 전부터 실패하던 테스트는 그대로 기록해 둔다. 나중에 리팩토링 탓으로 오인하지 않기 위해서다. `uv run mypy` 도 한 번 돌려 오류 수를 기록한다. 프로젝트가 아직 uv 를 쓰지 않으면 기존 방식으로 기준선을 먼저 잡고 나서 uv 로 옮긴다. 도구를 옮기다 깨진 것과 원래 깨져 있던 것을 구분하기 위해서다.

테스트가 없는 영역은 리팩토링 전에 특성 테스트를 쓴다. 특성 테스트는 올바른 동작이 아니라 **현재 동작**을 고정한다. 현재 코드가 이상한 값을 돌려주더라도 그 값을 그대로 단언한다. 목적은 리팩토링 전후가 같다는 걸 증명하는 것이다.

- 모듈의 공개 경계(HTTP 엔드포인트, 공개 함수)에서 쓴다. 내부 구현에 붙이면 리팩토링할 때 테스트도 같이 깨져서 증명이 안 된다. 그래서 리팩토링 전에 쓰는 특성 테스트는 대부분 `integ/` 에 들어간다.
- 리팩토링 전 코드에서 통과하는 걸 확인하고 나서 다음 단계로 간다.
- 외부 시스템 의존 때문에 테스트를 쓸 수 없는 모듈은 억지로 쓰지 않는다. 그 모듈을 변경 문서의 비고에 "미검증"으로 적는다.

`unit/` 테스트는 모듈별로 쓴다. 모듈 하나를 리팩토링할 때 그 모듈의 단위 테스트를 같은 단위 안에서 쓰고 통과시킨 뒤 다음 모듈로 간다. 나중에 몰아서 쓰지 않는다. 리팩토링이 끝났을 때 모든 모듈이 `tests/unit/` 에 자기 테스트를 가지고 있어야 한다.

### 리팩토링

- 모듈 단위로 고치고, 한 단위가 끝날 때마다 테스트를 돌린다. 전부 고친 뒤에 한 번에 돌리면 어느 변경이 깨뜨렸는지 찾을 수 없다.
- 동작을 바꾸지 않는다. 공개 API 의 경로, 요청과 응답 형태, DB 스키마, 설정 키 이름은 설계문서나 승인된 계획이 명시적으로 바꾸라고 한 경우에만 바꾼다.
- 작업 중 버그를 발견해도 리팩토링과 섞어 고치지 않는다. 동작이 바뀌면 전후 비교가 무의미해진다. 발견한 버그는 변경 문서의 비고에 적어 사용자가 따로 판단하게 한다. 타입 힌트를 붙이다 드러난 타입 불일치도 같은 방식으로 다룬다.
- 손대는 모듈마다 코드 규칙을 적용한다. 구조만 옮기고 타입 힌트와 모듈 docstring 을 나중으로 미루지 않는다.
- 포맷과 들여쓰기 같은 표기 방식은 기존 코드를 따른다. 모듈명, 타입 힌트, docstring 은 기존 코드에 없더라도 코드 규칙을 따른다.

### 검증

아래를 전부 돌려 기준선과 비교한다.

- `uv run pytest tests/unit` 과 `uv run pytest tests/integ`: 둘 다 돌리고 둘 다 통과해야 한다. 브랜치를 배포하기 전의 관문이다. 기준선에서 통과하던 테스트가 실패하면 리팩토링이 동작을 바꾼 것이니 코드를 고친다. 테스트를 고쳐서 통과시키지 않는다. 테스트 수정이 정당한 경우는 테스트가 내부 구현(옮겨진 import 경로 등)에 묶여 있을 때뿐이고, 그렇게 고친 테스트는 의도가 보존됐는지 확인한 뒤 비고에 적는다.
- `uv run mypy`: 리팩토링한 모듈에서 오류가 0이어야 한다.
- 의존 방향: 아래 층에서 위 층을 import 하는 줄이 없는지 grep 으로 확인한다.
- 기존 테스트의 의도: 분석 표의 테스트마다 같은 보장을 하는 테스트가 리팩토링 후에도 남아 있는지 대조한다.

돌려본 것만 "확인했다"고 쓴다. 실행하지 못한 검증은 못 했다고 쓴다.

## 변경 문서

리팩토링이 끝나면 반드시 쓴다. 코드만 고치고 문서 없이 끝내지 않는다.

- **위치**: 대상 서비스의 `docs/refactoring/YYYY-MM-DD-<서비스명>.md`. 날짜는 작업일. 같은 날 같은 서비스를 다시 리팩토링하면 새 파일을 만들지 않고 그 파일을 갱신한다.
- **구조**: `assets/change-doc-template.md` 를 그대로 따른다. 아래 세 절의 제목과 순서를 바꾸지 않는다.

```markdown
## 1. 개요
## 2. 리팩토링 내용
## 3. 비고 및 특이사항
```

**개요**에는 날짜, 작성자, 대상 서비스, 기준(설계문서 경로 또는 "기본 방안"), 기준 커밋, 검증 결과 요약을 적는다. 작성자는 `git config user.name`, 기준 커밋은 리팩토링 시작 시점의 `git rev-parse --short HEAD` 에서 가져온다. git 저장소가 아니면 해당 칸에 "없음"이라 쓴다. 검증 결과에는 pytest(unit, integ 각각)와 mypy 의 전후 수치를 적는다.

**리팩토링 내용**은 모듈마다 문단을 나누고, 문단마다 리팩토링 전과 후를 나란히 쓴다. 독자는 diff 를 보지 않고 이 문서만 읽는다고 가정한다.

- 전과 후는 구조를 서술한다. 코드를 줄 단위로 풀어 쓰지 않는다. 구조 차이를 말로 전하기 어려우면 짧은 코드 조각이나 디렉토리 트리를 쓴다.
- 변경 이유를 한두 문장으로 적는다. 설계문서 기반이면 설계문서의 어느 항목에 해당하는지 가리킨다.
- 파일이 옮겨지거나 이름이 바뀌었으면 옛 경로와 새 경로를 적는다.
- 테스트도 모듈로 다룬다. 테스트 구조가 어떻게 바뀌었는지, 기존 테스트가 어디로 갔는지, 무엇을 새로 썼는지 문단 하나로 적는다.
- 타입 힌트와 docstring 추가처럼 모든 모듈에 똑같이 적용한 변경은 모듈마다 되풀이하지 않고 "공통 적용" 문단 하나에 모은다.
- 손대지 않은 모듈은 문단을 만들지 않는다. 필요하면 비고에 한 줄로 적는다.

**비고 및 특이사항**에는 작업 중 생긴 특수한 경우를 적는다. 해당 사항이 없으면 "없음"이라 쓴다.

- 승인된 계획에서 벗어난 지점과 이유
- 테스트를 못 써서 검증하지 못한 모듈
- 발견했지만 고치지 않은 버그와 타입 불일치
- 내부 구현에 묶여 있어서 수정한 테스트
- 설계문서 지시 중 수행하지 못한 항목
- 설계문서와 코드 규칙이 부딪힌 지점과 사용자의 결정
- 배포할 때 사람이 해야 하는 일 (환경변수 추가, 마이그레이션 실행, uv 전환에 따른 설치 명령 변경 등)

## 끝내기 전에

- 변경 문서가 `docs/refactoring/` 에 있는가
- 변경 문서의 모듈 문단이 실제로 고친 모듈과 일치하는가. 고쳤는데 문서에 없는 모듈, 문서에 있는데 안 고친 모듈이 없어야 한다.
- `uv run pytest` 와 `uv run mypy` 를 마지막 수정 이후에 돌렸는가
- import 경로만 읽고 각 모듈의 역할을 알 수 있는가. 역방향 import 가 없는가
- 손댄 모든 `.py` 파일에 모듈 docstring 과 타입 힌트가 있는가
- logger 가 공통 모듈 하나에서만 설정되는가
- 테스트가 `tests/unit/` 과 `tests/integ/` 로 나뉘어 있고 둘 다 통과하는가. 모든 모듈이 단위 테스트를 가지고, 모든 엔드포인트가 시나리오에 등장하는가
- 기존 테스트의 의도가 전부 남아 있는가
- `ABC` 로 만든 추상 클래스가 승인 없이 들어가 있지 않은가
- 엔드포인트마다 기능 설명, 인자 설명, 사용 예제가 있는가
- 미검증 모듈과 발견한 버그가 비고에 적혀 있는가

마지막 보고는 짧게 한다. 변경 문서 경로, 테스트와 mypy 결과(기준선 대비), 사용자가 결정해야 할 비고 항목.

## 범위 밖

- 새 기능 추가와 버그 수정. 동작이 바뀌는 작업은 리팩토링이 아니다.
- 서비스를 처음부터 새로 만드는 일.
- 프레임워크, 언어, DB 종류 교체.
- 커밋과 푸시. 사용자가 요청하면 그때 한다.
