# 2단계: 설계

`research_kit` 의 참조 문서. 가설과 관련 연구를 알고, 어떤 실험을 어떻게 돌릴지 정할 때 읽는다.

이 단계의 산출물은 `research/<slug>/design.md` 다. `assets/design-template.md` 를 복사해 채운다. **실행 전에 평가 기준과 임계값까지 채워야 끝난다.**

설계는 두 층이다. 연구 전체에 공통인 것(가설, 평가 기준, 평가셋, seed, 예산)과 실험마다 다른 것(목표, 무엇을 바꾸고 무엇을 고정하는지). 보고서의 "실험내용" 절은 실험 목록에서 그대로 나오므로, 실험 하나의 목표가 한 문장으로 안 써지면 그 실험은 둘로 나눈다.

---

## 순서

### 1. 가설을 반증 가능한 문장으로

`hypothesis.md` 의 가설을 "X 하면 Y 가 Z 만큼 달라진다"의 형태로 다듬는다. 어떤 결과가 나오면 틀린 것인지 말할 수 없는 가설은 검증할 수 없다.

| 검증할 수 없음 | 검증할 수 있음 |
|---|---|
| CoT 가 추론에 도움이 된다 | Llama-3-8B 에서 8-shot CoT 는 8-shot direct 대비 GSM8K test 정확도를 3%p 이상 높인다 |
| 데이터 증강이 효과적이다 | 역번역 증강 2배는 증강 없음 대비 held-out F1 을 seed 3개 평균에서 1.0 이상 높인다 |

귀무가설(차이 없음)도 같이 적는다. 판단 단계에서 어느 쪽을 택하는지 분명해진다.

### 2. 실험 목록

가설 하나를 확인하는 데 실험이 여럿 필요할 수 있다. 실험마다 아래를 표로 적는다.

- **exp-id**: 영어 소문자와 하이픈. 폴더 이름이 된다
- **목표**: 한 문장. "모델 4종에서 CoT 효과가 모델 크기에 따라 달라지는지 본다"
- **바꾸는 것**: 독립 변인과 그 값들. **하나만.**
- **고정하는 것**: 이 실험에서 통제한 것. "같은 평가셋 500문항, 같은 프롬프트, greedy"
- **가설의 어느 부분을 확인하는가**

실험 수는 목표를 확인하는 데 필요한 최소로 한다. 보고서를 읽는 사람이 "이 실험은 왜 했지?"라고 물을 실험은 빼거나 탐색으로 표시한다.

### 3. 변인 정하기

실험마다 적는다.

- **독립 변인**: 바꾸는 것. **하나만.** 여러 개를 보고 싶으면 실험을 나누거나 조건을 격자로 만들되 각 비교쌍은 한 변인만 다르게 한다.
- **종속 변인**: 측정하는 것. 주 기준 하나, 보조 기준은 필요한 만큼. 아래 5번의 평가 기준에서 고른다.
- **통제 변인**: 고정하는 것. 명시적으로 적는다. 적지 않은 통제 변인은 조건 사이에서 몰래 달라진다. 자주 빠지는 것: 디코딩 설정, max tokens, 시스템 프롬프트, 토크나이저 버전, 데이터 전처리, 학습 스텝 수.

### 4. 비교군

- **베이스라인**: 1단계 `survey.md` 의 자원 표에서 고른다. 가장 강한 합리적 베이스라인을 쓴다. 약한 베이스라인을 이긴 결과는 아무것도 증명하지 않는다.
- **자명한 기준선**: 다수 클래스 예측, 무작위, 프롬프트 없는 zero-shot 같은 바닥 기준. 제안 방법이 이것도 못 넘으면 설정이 망가진 것이다.
- **ablation**: 제안 방법이 여러 요소로 되어 있으면, 요소를 하나씩 뺀 조건. 어느 요소가 효과를 내는지 보려면 필요하다.

### 5. 평가 기준

평가는 신뢰할 수 있고 흠 없는 기준으로 판단을 내리는 일이다. 기준이 흔들리면 그 위의 모든 숫자가 흔들린다. 기준마다 다섯 가지를 적는다.

| 항목 | 내용 | 예 |
|---|---|---|
| 이름 | 보고서에 쓸 이름 | 정확도, faithfulness |
| 출력 형식 | 아래 셋 중 하나 | true/false |
| 산출 규칙 | 원 출력에서 이 값을 어떻게 뽑는가. 누가 해도 같은 값이 나오게 | `####` 뒤 숫자를 정규화해 정답과 정확 일치 |
| 신뢰 근거 | 이 기준이 믿을 만한 이유 한 줄 | GSM8K 공식 채점 스크립트 그대로 |
| 임계값 | 몇 이상이면 통과인가. 판단 단계에서 그대로 대입 | base 대비 +3%p 이상 |

출력 형식은 셋 중 하나다.

- **true/false**: 옳고 그름. 정답 일치, 제약 충족 여부, 테스트 통과.
- **다중 선택지**: 적정, 부적정, 측정 불가처럼 정해진 선택지 중 하나. 선택지 목록과 각 선택지의 조건을 적는다. "측정 불가"처럼 판정을 내릴 수 없는 경우를 받는 선택지를 두어야 억지 판정이 안 생긴다.
- **정규화 점수**: 1~100 또는 0~1 처럼 범위가 정해진 점수. 범위, 산출식, 점수 간격의 뜻(50점과 60점의 차이가 무엇인지)을 적는다.

신뢰 근거로 쓸 수 있는 것:

- 표준 벤치마크의 공식 채점 규칙이나 스크립트를 그대로 쓴다
- 결정적 규칙(정확 일치, 정규식, 단위 테스트)이라 재채점해도 같은 값이 나온다
- 사람 라벨 표본 N 개와 일치율 X 이상을 확인했다(또는 평가 전에 확인할 계획)
- 같은 입력을 두 번 채점해 일치율 X 이상을 확인했다(LLM-judge 처럼 비결정적인 채점일 때)

신뢰 근거를 한 줄로 못 쓰는 기준은 쓰지 않는다. "그럴듯한 점수"는 기준이 아니다.

**주 기준은 하나**다. 여러 기준 중 좋은 것만 골라 보고하는 걸 막는다. 보조 기준은 결과를 설명하는 데만 쓰고 판단에는 쓰지 않는다.

### 6. 평가셋

- 출처, 분할, 크기, 버전(해시나 날짜)을 적는다.
- 개발용과 최종 평가용을 나눈다. 하이퍼파라미터를 고르는 데 쓴 셋으로 최종 성능을 보고하지 않는다.
- 모든 조건을 **같은 항목 집합**으로 평가한다. 항목이 다르면 조건 간 차이가 방법 차이인지 항목 난이도 차이인지 알 수 없다.

### 7. 반복 수와 seed

- 학습이 들어가면 seed 최소 3개. 임계값이 작은 차이면 5개.
- 추론만 하는 LLM 평가는 greedy 면 1회로 충분하지만, sampling 이면 반복 N 회와 seed 목록을 적는다.
- seed 목록은 설계에 미리 적는다(`[0, 1, 2]`). 결과를 보고 seed 를 고르는 걸 막는다.
- seed 가 여럿이면 평가와 보고서에 평균 옆에 표준편차와 N 을 적는다. 조건 간 차이가 표준편차보다 작으면 판단에서 "차이 있음"으로 쓰지 않는다. 이 규칙을 설계에 적어 둔다.

### 8. 판정 규칙

실행 전에 이렇게 적는다. 판단 단계에서 숫자를 그대로 대입한다.

- **지지**: <주 기준에서 base 대비 차이가 X 이상이고, seed 표준편차의 2배보다 큼>
- **기각**: <차이가 X 미만이거나 음수>
- **판정 불가**: <그 외. 차이가 X 근처인데 seed 분산이 커서 가를 수 없음, 또는 기준 미충족 항목이 남음>

### 9. 계산 예산과 실행 계획

실험 수 × 조건 수 × seed 수 × 실행당 비용(GPU 시간 또는 API 토큰과 금액)을 계산해 적는다. 예산을 넘으면 조건을 줄이거나 작은 모델로 먼저 확인하는 단계적 계획을 세운다. 이 판단은 사용자 몫이므로 AskUserQuestion 으로 묻는다.

### 10. 실험 코드 형태

실험마다 모듈(`run.py`)로 할지 노트북(`run.ipynb`)으로 할지 정한다. 기본은 모듈이다. 반복 실행과 seed 별 실행을 명령 한 줄로 돌릴 수 있고, 카드에 적을 실행 명령이 명확하다. 노트북은 사용자가 탐색적으로 보면서 돌리고 싶을 때 고른다. 어느 쪽이든 규칙은 `references/verification.md` 에 있다. 사용자가 선호를 말하지 않았으면 AskUserQuestion 으로 한 번 묻는다.

## 유형별 주의점

### LLM 평가

- **디코딩 설정 고정**: temperature, top_p, max tokens, stop 토큰, 시스템 프롬프트를 통제 변인에 적는다. API 모델이면 모델 스냅샷 이름(날짜가 붙은 버전)을 쓴다. 별칭(`latest`)은 조건 사이에 바뀔 수 있다.
- **오염**: 공개 벤치마크는 학습 데이터에 섞였을 수 있다. 가능하면 모델 학습 시점 이후에 만들어진 평가셋이나 자체 평가셋을 같이 쓴다.
- **답 추출**: 산출 규칙에 정답 판정 규칙(정규식, 정확 일치, 정규화)을 적는다. 추출 규칙 차이만으로 수 %p 가 달라진다. 추출 실패(빈 예측, 파싱 에러)를 오답으로 셀지 제외할지도 미리 정한다.
- **LLM-judge 를 쓰면**: judge 모델과 프롬프트를 고정하고, 신뢰 근거로 사람 라벨 표본(최소 50개)과의 일치율 또는 재채점 일치율을 평가 전에 확인할 계획을 넣는다. 위치 편향을 막기 위해 A/B 순서를 뒤바꾼 두 번 평가를 계획한다.

### 비교대조 실험

- **같은 평가 항목**: 모든 조건을 같은 항목 집합으로 평가한다.
- **주 비교 하나**: 조건이 3개 이상이면 비교쌍이 늘어난다. 주 비교(보통 제안 vs 최강 베이스라인)를 미리 하나 정하고, 나머지는 탐색 비교로 표시한다.

### 모델 학습과 파인튜닝

- **계산 동등성**: 조건 간 학습 스텝, 토큰 수, 또는 FLOPs 중 무엇을 맞출지 정한다. 한쪽만 더 오래 학습시키면 효과가 방법 때문인지 계산 때문인지 알 수 없다.
- **체크포인트 선택**: 어느 체크포인트를 평가할지(마지막, 검증 손실 최저) 미리 정한다. 테스트 성능을 보고 고르지 않는다.
- **하이퍼파라미터 탐색 예산**: 제안 방법에만 튜닝을 많이 하면 불공정하다. 베이스라인에도 같은 탐색 예산을 쓴다.

### 새 가설 탐색

- **대조 조건 먼저**: 새 현상을 주장하려면 "그 현상이 없을 때"와 비교해야 한다. 대조 조건을 어떻게 만들지가 설계의 대부분이다.
- **대안 설명 나열**: 결과가 가설대로 나와도 다른 이유로 설명될 수 있는 경로를 미리 적고, 각각을 배제할 조건을 설계에 넣는다.
- **탐색과 확증 분리**: 처음 실험은 탐색으로 표시하고, 거기서 나온 패턴은 새 데이터로 확증 실험을 한 번 더 한다.

## 끝내기 전 확인

- [ ] 가설이 반증 가능한 문장인가
- [ ] 실험마다 목표가 한 문장이고, 바꾸는 것이 하나인가
- [ ] 통제 변인이 실험마다 목록으로 적혀 있는가
- [ ] 주 기준이 하나이고, 기준마다 출력 형식, 산출 규칙, 신뢰 근거, 임계값이 있는가
- [ ] seed 목록이 적혀 있는가
- [ ] 판정 규칙(지지, 기각, 판정 불가)이 숫자로 적혀 있는가
- [ ] 계산 예산을 사용자가 확인했는가
- [ ] 실험 코드 형태(모듈 또는 노트북)를 정했는가

하나라도 비었으면 3단계로 넘어가지 않고 사용자에게 알린다.
