# 2단계 — 가설·실험 설계

`research_kit` 의 참조 문서. 검증할 질문이나 비교할 조건이 정해졌을 때 읽는다.

이 단계의 산출물은 `research/<slug>/design.md` 다. `assets/design-template.md` 를 복사해 채운다. **실행 전에 판정 기준까지 채워야 끝난다.**

---

## 순서

### 1. 가설을 반증 가능한 문장으로

가설은 "X 하면 Y 가 Z 만큼 달라진다"의 형태여야 한다. 어떤 결과가 나오면 틀린 것인지 말할 수 없는 가설은 검증할 수 없다.

| 검증할 수 없음 | 검증할 수 있음 |
|---|---|
| CoT 가 추론에 도움이 된다 | Llama-3-8B 에서 8-shot CoT 는 8-shot direct 대비 GSM8K test 정확도를 3%p 이상 높인다 |
| 데이터 증강이 효과적이다 | 역번역 증강 2배는 증강 없음 대비 held-out F1 을 seed 3개 평균에서 1.0 이상 높인다 |

귀무가설(차이 없음)도 같이 적는다. 분석 단계에서 어느 쪽을 기각하는지 분명해진다.

### 2. 변인 정하기

- **독립 변인** — 바꾸는 것. **하나만.** 여러 개를 보고 싶으면 조건을 격자로 만들되 각 비교쌍은 한 변인만 다르게 한다.
- **종속 변인** — 측정하는 것. 주 지표 하나, 보조 지표는 필요한 만큼.
- **통제 변인** — 고정하는 것. 명시적으로 적는다. 적지 않은 통제 변인은 조건 사이에서 몰래 달라진다. 자주 빠지는 것: 디코딩 설정, max tokens, 시스템 프롬프트, 토크나이저 버전, 데이터 전처리, 학습 스텝 수.

### 3. 비교군

- **베이스라인** — 1단계 `survey.md` 의 베이스라인 표에서 고른다. 가장 강한 합리적 베이스라인을 쓴다. 약한 베이스라인을 이긴 결과는 아무것도 증명하지 않는다.
- **자명한 기준선** — 다수 클래스 예측, 무작위, 프롬프트 없는 zero-shot 같은 바닥 기준. 제안 방법이 이것도 못 넘으면 설정이 망가진 것이다.
- **ablation** — 제안 방법이 여러 요소로 되어 있으면, 요소를 하나씩 뺀 조건. 어느 요소가 효과를 내는지 보려면 필요하다.

### 4. 평가 지표와 평가셋

- 주 지표를 **하나** 정한다. 여러 지표 중 좋은 것만 골라 보고하는 걸 막는다.
- 평가셋의 출처, 분할, 크기, 버전(해시나 날짜)을 적는다.
- 개발용과 최종 평가용을 나눈다. 하이퍼파라미터를 고르는 데 쓴 셋으로 최종 성능을 보고하지 않는다.
- 표본 크기가 판정 기준의 차이를 잡을 수 있는지 대략 확인한다. 정확도 기준으로 평가셋 N 개일 때 95% 신뢰구간의 반폭은 대략 `1.96 × sqrt(p(1-p)/N)` 이다. p=0.7, N=200 이면 ±6.4%p 라서 3%p 차이는 잡기 어렵다 — 그러면 평가셋을 늘리거나 쌍체 분석(4단계)에 기대야 한다고 적는다.

### 5. 반복 수와 seed

- 학습이 들어가면 seed 최소 3개. 판정 기준이 작은 차이면 5개.
- 추론만 하는 LLM 평가는 greedy 면 1회로 충분하지만, sampling 이면 반복 N 회와 seed 목록을 적는다.
- seed 목록은 설계에 미리 적는다(`[0, 1, 2]`). 결과를 보고 seed 를 고르는 걸 막는다.

### 6. 판정 기준

실행 전에 이렇게 적는다.

- **지지**: <주 지표에서 차이가 X 이상이고 95% 신뢰구간이 0 을 포함하지 않음>
- **기각**: <신뢰구간 전체가 X 미만>
- **판정 불가**: <그 외 — 신뢰구간이 X 와 0 을 모두 걸침>

### 7. 계산 예산과 실행 계획

조건 수 × seed 수 × 실행당 비용(GPU 시간 또는 API 토큰·금액)을 계산해 적는다. 예산을 넘으면 조건을 줄이거나 작은 모델로 먼저 확인하는 단계적 계획을 세운다. 이 판단은 사용자 몫이므로 AskUserQuestion 으로 묻는다.

## 유형별 주의점

### LLM 평가

- **디코딩 설정 고정** — temperature, top_p, max tokens, stop 토큰, 시스템 프롬프트를 통제 변인에 적는다. API 모델이면 모델 스냅샷 이름(날짜가 붙은 버전)을 쓴다. 별칭(`latest`)은 조건 사이에 바뀔 수 있다.
- **오염** — 공개 벤치마크는 학습 데이터에 섞였을 수 있다. 가능하면 모델 학습 시점 이후에 만들어진 평가셋이나 자체 평가셋을 같이 쓴다.
- **답 추출** — 정답 판정 규칙(정규식, 정확 일치, 정규화)을 설계에 적는다. 추출 규칙 차이만으로 수 %p 가 달라진다.
- **LLM-judge 를 쓰면** — judge 모델과 프롬프트를 고정하고, 사람 라벨과의 일치도를 볼 표본(최소 50개)을 계획에 넣는다. 위치 편향을 막기 위해 A/B 순서를 뒤바꾼 두 번 평가를 계획한다.

### 비교대조 실험

- **같은 평가 항목** — 모든 조건을 같은 항목 집합으로 평가한다. 그래야 4단계에서 쌍체 분석을 할 수 있고, 쌍체 분석은 같은 표본 크기로 훨씬 작은 차이를 잡는다.
- **다중 비교** — 조건이 3개 이상이면 비교쌍이 늘어난다. 주 비교(보통 제안 vs 최강 베이스라인)를 미리 하나 정하고, 나머지는 탐색 비교로 표시한다.

### 모델 학습·파인튜닝

- **계산 동등성** — 조건 간 학습 스텝, 토큰 수, 또는 FLOPs 중 무엇을 맞출지 정한다. 한쪽만 더 오래 학습시키면 효과가 방법 때문인지 계산 때문인지 알 수 없다.
- **체크포인트 선택** — 어느 체크포인트를 평가할지(마지막, 검증 손실 최저) 미리 정한다. 테스트 성능을 보고 고르지 않는다.
- **하이퍼파라미터 탐색 예산** — 제안 방법에만 튜닝을 많이 하면 불공정하다. 베이스라인에도 같은 탐색 예산을 쓴다.

### 새 가설 탐색

- **대조 조건 먼저** — 새 현상을 주장하려면 "그 현상이 없을 때"와 비교해야 한다. 대조 조건을 어떻게 만들지가 설계의 대부분이다.
- **대안 설명 나열** — 결과가 가설대로 나와도 다른 이유로 설명될 수 있는 경로를 미리 적고, 각각을 배제할 조건을 설계에 넣는다.
- **탐색과 확증 분리** — 처음 실험은 탐색으로 표시하고, 거기서 나온 패턴은 새 데이터로 확증 실험을 한 번 더 한다.

## 끝내기 전 확인

- [ ] 가설이 반증 가능한 문장인가
- [ ] 독립 변인이 비교쌍마다 하나인가
- [ ] 통제 변인이 목록으로 적혀 있는가
- [ ] 주 지표가 하나인가
- [ ] seed 목록이 적혀 있는가
- [ ] 판정 기준(지지/기각/판정 불가)이 숫자로 적혀 있는가
- [ ] 계산 예산을 사용자가 확인했는가

하나라도 비었으면 3단계로 넘어가지 않고 사용자에게 알린다.
