# 4단계: 평가

`research_kit` 의 참조 문서. 실행 결과가 있고 설계한 기준으로 채점할 때 읽는다.

이 단계의 산출물은 `research/<slug>/evaluation.md` 다. `assets/evaluation-template.md` 를 채운다. 평가는 설계에 적힌 기준을 **그대로** 적용하는 일이다. 새 기준을 만들거나 기준을 고치는 일은 여기서 하지 않는다.

평가는 신뢰할 수 있고 흠 없는 기준으로 판단을 내리는 일이고, 그래서 평가 결과가 성능을 대변한다. 기준을 그대로 적용할 수 없는 상황이 생기면 그 전제가 깨진다. 그때는 멈추고 사용자에게 묻는다. 이 단계에서 가장 중요한 규칙이다.

---

## 시작 전 확인

- `design.md` 에 평가 기준(출력 형식, 산출 규칙, 신뢰 근거, 임계값)이 있는가. 없으면 사용자가 가져온 결과를 채점하되, `evaluation.md` 머리에 "사전 기준 없음, 탐색 결과"라고 명시한다. 이미 본 결과로 기준을 소급해 만들지 않는다.
- `experiments/*/runs/` 의 실험 × 조건 × seed 조합이 다 찼는가. 빠졌으면 무엇이 빠졌는지 적고, 빠진 조건은 비교에서 뺀다.
- 카드 구분이 **탐색**인 실행은 판단 근거에서 제외한다. 탐색 실행의 숫자는 `evaluation.md` 에 따로 표시해 적을 수는 있다.

## 순서

### 1. 기준 충족 점검

채점하기 전에 기준을 그대로 적용할 수 있는지 본다. 아래 하나라도 걸리면 **멈추고 AskUserQuestion** 으로 처리 방법을 묻는다. 선택지에는 해당 항목 제외, 오답 처리, 규칙 보완 후 재채점, 평가 보류를 넣고, 사용자의 결정과 이유를 `evaluation.md` 의 "기준 미충족과 처리" 절에 남긴다.

- **산출 규칙에 안 맞는 출력**: 모델이 설계한 형식(`####` 뒤 숫자, JSON 키)을 안 지켜 규칙으로 값을 못 뽑는 항목. 비율을 조건별로 센다. 조건마다 비율이 다르면 이 차이만으로 주 기준이 달라진다.
- **신뢰 근거 미확인**: 설계에서 "사람 라벨 50개와 일치율 확인"이나 "재채점 일치율 확인"을 계획했는데 아직 안 했거나, 했는데 임계값에 못 미친다. 이 경우 judge 결과로 판단하지 않는다.
- **평가셋 불일치**: 실행에 쓴 평가셋의 버전이나 항목 수가 설계와 다르다. 조건마다 평가 항목이 다르다.
- **출력 형식 불일치**: 결과가 설계한 형식(true/false, 선택지, 점수 범위)으로 안 나온다. 점수 범위 밖의 값, 선택지에 없는 값.
- **설계와 다른 실행**: 카드의 "design.md 와 다른 점"이 비어 있지 않다.

임의로 "이 정도는 괜찮다"고 넘기지 않는다. 사용자가 괜찮다고 하면 그 결정이 기록으로 남고, 보고서의 한계에 들어간다.

### 2. 이상 점검

숫자를 비교하기 전에 숫자가 멀쩡한지 본다.

- 자명한 기준선보다 낮은 조건이 있는가. 설정이 망가졌을 가능성
- 베이스라인이 `survey.md` 의 보고 수치와 크게 다른가. 평가 설정 차이를 먼저 설명
- seed 간 분산이 조건 간 차이보다 큰가. 판정 불가 쪽으로 기운다
- 추출 실패 비율이 조건마다 다른가. 실패율을 따로 보고한다

LLM 평가면 오답 표본 20개 정도를 직접 읽는다. 기준이 잡지 못하는 문제(채점 규칙 오류, 형식만 다른 정답)가 여기서 드러난다. 발견하면 1번으로 돌아가 사용자에게 묻는다.

### 3. 채점과 집계

기준마다 설계의 산출 규칙을 코드로 적용한다. 채점 코드는 `research/<slug>/evaluate.py` 로 저장하거나 `evaluation.md` 에 붙인다. **같은 `runs/` 에 다시 돌리면 같은 숫자가 나와야 한다.** 비결정적 채점(LLM-judge)이면 judge 응답도 저장해 재집계 때 다시 부르지 않게 한다.

집계 표는 실험마다 하나. 조건이 행, 기준이 열.

```
| 조건 | 주 기준 (평균 ± 표준편차, N) | 보조 기준 | 추출 실패율 | seed 수 |
|---|---|---|---|---|
| base | 71.5 ± 0.8 (N=500) | | 0.4% | 3 |
| prop | 74.2 ± 1.1 (N=500) | | 1.2% | 3 |
```

- seed 가 여럿이면 평균 옆에 표준편차와 N 을 **항상** 적는다. seed 가 하나면 "seed 1개"라고 적는다.
- 출력 형식이 true/false 면 비율(%), 다중 선택지면 선택지별 개수와 비율, 정규화 점수면 평균과 표준편차와 분포(그림).
- 주 비교(설계에서 정한 조건쌍)의 차이를 따로 한 줄로 적는다. "prop − base = +2.7%p, 두 조건의 표준편차 0.8, 1.1".

### 4. 그림

보고서의 실험마다 그림이 하나 이상 들어간다. 검증 단계에서 만들지 않았으면 여기서 만든다.

- 조건 비교는 막대 또는 점과 오차 막대(표준편차). 학습 곡선은 조건별로 겹친 선.
- 제목, 축 이름, 단위, 범례가 그림 안에. 파일은 `experiments/<exp-id>/figures/<exp-id>-<내용>.png`.
- 그림의 숫자는 집계 표와 같은 코드에서 나온다. 표와 그림이 다른 숫자를 보이면 둘 다 못 믿는다.

### 5. 보조 비교

ablation, 보조 기준, 주 비교 외의 조건쌍. 주 비교와 같은 표 형식으로 적되 **탐색 비교**라고 표시한다. 여기서 나온 흥미로운 패턴은 결론이 아니라 다음 가설이다.

### 6. 대안 설명 점검

`design.md` 의 "대안 설명과 배제 방법"을 하나씩 확인한다. 배제하지 못한 대안 설명은 판단 단계와 보고서의 한계로 넘긴다.

## 유형별 주의점

### LLM 평가

- **LLM-judge**: A/B 순서를 바꿔 두 번 평가해서 두 판정이 엇갈린 비율(위치 편향)을 보고한다. 엇갈린 항목은 무승부로 처리하거나 제외하고 그 규칙을 적는다. 설계의 신뢰 근거(사람 라벨 일치율, 재채점 일치율)를 실제 값으로 채운다. 임계값에 못 미치면 1번 규칙대로 멈춘다.
- **길이 편향**: judge 가 긴 답을 선호하는지 본다. 조건 간 평균 응답 길이를 같이 보고한다.
- **자기 선호**: judge 와 평가 대상이 같은 모델 계열이면 그 사실을 적는다.

### 모델 학습

- 학습 곡선(손실, 검증 지표)을 조건별로 겹쳐 본다. 한 조건만 아직 수렴 중이면 스텝 수가 부족한 것이지 방법이 나쁜 게 아닐 수 있다.
- 최종 수치는 설계에서 정한 체크포인트 기준으로만 보고한다.

### 새 가설 탐색

- 첫 실험 결과는 탐색으로 보고한다. "확증하려면 새 데이터로 무엇을 다시 해야 하는가"를 다음 실험에 적는다.

## 끝내기 전 확인

- [ ] 기준 미충족 항목이 모두 사용자 결정으로 처리됐는가 (보류 상태면 5단계로 넘어가지 않는다)
- [ ] 실험마다 집계 표와 그림이 있는가
- [ ] 주 비교의 차이와 seed 분산이 한 줄로 적혀 있는가
- [ ] 채점 코드가 저장돼 있고 다시 돌려도 같은 숫자가 나오는가
- [ ] 제외한 실행과 이유가 적혀 있는가
