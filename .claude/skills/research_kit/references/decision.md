# 5단계: 판단과 보고서

`research_kit` 의 참조 문서. 평가가 끝났고 "이 결과를 본 연구에 쓸 수 있는가"를 정할 때, 그리고 보고서를 쓸 때 읽는다.

이 단계의 산출물은 둘이다. `decision.md` 는 판단과 근거, `report.md` 는 남에게 보여줄 보고서. 판단이 먼저고 보고서는 판단을 옮겨 적는다. 보고서를 쓰면서 판단이 바뀌면 `decision.md` 를 먼저 고친다.

---

## 판단

### 질문

판단은 가설이 맞았는지보다 한 층 위의 질문에 답한다. **이 실험의 결과를 본 연구에 쓸 수 있는가.** 가설이 지지돼도 조건이 너무 좁아 본 연구에 못 쓸 수 있고, 가설이 기각돼도 "이 방향은 아니다"가 본 연구에 쓸 수 있는 결과일 수 있다.

### 순서

1. **가설 판정**: `design.md` 의 판정 규칙에 `evaluation.md` 의 주 비교 숫자를 그대로 대입한다. 지지, 기각, 판정 불가 중 하나. 규칙이 요구한 조건을 인용하고 실제 값을 옆에 쓴다.
2. **조건 확인**: 지지라면 어떤 조건(모델, 데이터, 규모)에서 성립했는지, 본 연구의 조건과 같은지 본다. 실험 조건이 본 연구보다 좁으면 그 차이를 적는다.
3. **한계 확인**: `evaluation.md` 의 기준 미충족 처리, 배제 못 한 대안 설명, seed 수, 오염 가능성을 모은다. 이 중 결론을 바꿀 수 있는 것이 있는지 본다.
4. **결정**: 아래 넷 중 하나.

| 결정 | 뜻 | 다음 행동 |
|---|---|---|
| **채택** | 결과를 본 연구에 그대로 쓴다 | 본 연구의 어디에 어떻게 반영하는지 |
| **조건부 채택** | 특정 조건 안에서만 쓴다 | 조건을 명시. 조건 밖으로 넓히려면 어떤 실험이 필요한지 |
| **기각** | 이 결과는 본 연구에 쓰지 않는다 | 가설을 고칠지, 다른 접근을 볼지. 기각 자체가 본 연구에 주는 정보 |
| **판정 불가** | 지금 결과로는 정할 수 없다 | 무엇이 부족한지(표본, seed, 기준 미충족)와 그것을 채울 실험 |

### 규칙

- **근거는 `evaluation.md` 의 숫자만.** 평가에 없는 숫자, 실행하지 않은 조건의 예상치로 판단하지 않는다.
- **판정 불가를 포장하지 않는다.** "경향이 보인다", "개선 가능성이 있다"로 쓰지 않는다. 판정 불가는 그 자체로 정보다. 무엇이 더 필요한지 적는다.
- **seed 분산을 넘지 못한 차이는 차이가 아니다.** 조건 간 차이가 seed 표준편차 안에 있으면 지지로 쓰지 않는다.
- **채택의 범위를 과장하지 않는다.** 7B 모델 하나에서 본 결과를 "LLM 전반"으로 쓰지 않는다. 실험한 조건이 채택의 조건이다.
- **다음 행동은 구체적으로.** "추가 연구 필요"가 아니라 무엇을, 왜, 어떤 설계로. 다음 실험이 같은 가설이면 2단계로, 가설을 고쳐야 하면 `hypothesis.md` 를 고치고 1단계로 돌아간다.

`assets/decision-template.md` 를 채운다.

## 보고서

보고서는 판단의 근거가 된 실제 데이터(`runs/` 또는 사용자가 준 항목별 결과)가 있을 때만 쓴다. 데이터가 오기 전이면 `decision.md` 까지만 쓰고, 보고서는 데이터를 받은 뒤로 미룬다고 알린다. 추정으로 채운 보고서는 나중에 결론처럼 인용된다.

사용자가 그래도 지금 쓰라고 하면 쓰되, 초안이라는 것이 파일만 봐도 드러나게 한다. 제목 앞에 `[초안]`, metainfo 표에 "확정 조건: <무엇이 오면 확정>" 한 줄, 채울 수 없는 칸은 `[미확인]`, 그림은 `[그림 없음: <어느 run 의 어느 지표로 그릴지>]`. 없는 수치를 그럴듯한 값으로 메우지 않는다. 확정 조건이 채워지면 같은 파일을 고쳐 `[초안]` 을 뗀다.

### 템플릿

`assets/report-template.md` 의 구조를 **그대로** 쓴다. 절을 빼거나 이름을 바꾸지 않는다. 보고서 형태가 실험마다 다르면 여러 보고서를 나란히 읽을 수 없다.

```
# Title
metainfo 표 (실험 배경, 실험 목적, 실험 수행자, 실험 날짜)
## 개요
## 실험내용
  ### <실험 하나>
    목표 / 변인 통제 내역 / 결과 + figure / 결론 및 특이사항
## 결론
```

### 채우는 규칙

- **Title**: 결론을 담은 한 문장. "CoT 는 7B 이상에서만 GSM8K 정확도를 높인다". "CoT 실험 보고서"처럼 내용 없는 제목은 쓰지 않는다.
- **metainfo**: 실험 배경은 `hypothesis.md` 의 연구 주제와 이 실험이 맡는 역할. 실험 목적은 가설 한 문장. 실험 수행자는 사용자가 지정한 이름, 없으면 `git config user.name`. 실험 날짜는 `runs/` 카드의 첫 실행일부터 마지막 실행일까지.
- **개요**: 목적과 환경을 서술. 환경은 모델, 데이터셋과 버전, 하드웨어 또는 API, 주 기준과 신뢰 근거. 카드의 환경 절에서 가져온다. 5~8문장.
- **실험내용**: `design.md` 의 실험 목록 순서대로, 실험 하나당 소절 하나. 과도하게 쪼개지 않는다. 목표가 한 문장으로 서지 않는 소절은 둘로 나누거나 합친다. 각 소절에 네 항목이 **반드시** 있다.
  - **목표**: 설계의 목표 한 문장 그대로.
  - **변인 통제 내역**: 무엇을 고정하고 무엇만 바꿨는지. "같은 평가셋 500문항, 같은 프롬프트, greedy 로 고정하고 모델만 4종". 설계의 "바꾸는 것"과 "고정하는 것"에서 가져온다.
  - **결과 + figure**: `evaluation.md` 의 집계 표와 `figures/` 의 그림. 표에는 seed 분산과 N. 그림은 `![](experiments/<exp-id>/figures/<파일>)` 로 연결하고 한 줄 설명을 붙인다. 모든 숫자는 어느 run 이나 `evaluation.md` 의 어느 절에서 나왔는지 추적할 수 있어야 한다.
  - **결론 및 특이사항**: 이 실험이 가설의 어느 부분에 무엇을 말해 주는지 한두 문장. 특이사항은 이상 점검 결과, 기준 미충족 처리, 추출 실패율 차이, 설계에서 벗어난 것.
- **결론**: `decision.md` 를 옮겨 적는다. 첫 문장에 가설 판정과 결정(채택, 조건부 채택, 기각, 판정 불가). 둘째 문장에 주 비교의 숫자. 이어서 채택의 조건, 한계, 다음 행동. 독자가 이 절만 읽고 떠날 수 있어야 한다.

### 문장

- 모든 수치는 `runs/` 나 `evaluation.md` 에서 나온다. 실행하지 않은 조건의 수치는 쓰지 않는다.
- 한계를 숨기지 않는다. 기준 미충족을 사용자 결정으로 넘긴 항목, 배제하지 못한 대안 설명, 작은 seed 수, 오염 가능성, 탐색 비교.
- 헤지("~일 수도 있다")는 실제로 불확실한 곳에만 쓰고, 불확실한 이유를 같이 쓴다.
- 평가 대신 사실. "눈에 띄게 좋아졌다" 대신 "+2.7%p (표준편차 0.8, 1.1)".

### 끝내기 전 확인

- [ ] 템플릿의 절이 전부 있고 이름이 같은가
- [ ] 실험 소절마다 목표, 변인 통제 내역, 결과 + figure, 결론 및 특이사항이 있는가
- [ ] 그림 파일이 실제로 존재하고 경로가 맞는가
- [ ] 결론의 결정이 `decision.md` 와 같은가
- [ ] 보고서의 모든 숫자가 `evaluation.md` 에 있는가
