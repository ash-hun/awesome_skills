# 4단계 — 분석·보고서

`research_kit` 의 참조 문서. 실행 결과나 로그가 있을 때 읽는다.

이 단계의 산출물은 둘이다. `analysis.md` 는 계산과 판정의 작업 기록, `report.md` 는 남에게 보여줄 결론. 보고서는 `assets/report-template.md` 를 따른다.

---

## 시작 전 확인

- `design.md` 가 있는가. 없으면 사용자가 가져온 결과를 분석하되, 보고서에 "사전 판정 기준 없음 — 탐색 결과"라고 명시한다. 이미 본 결과로 판정 기준을 소급해 만들지 않는다.
- `runs/` 의 조건 × seed 조합이 다 찼는가. 빠졌으면 무엇이 빠졌는지 적고, 빠진 조건은 비교에서 뺀다.
- 카드 구분이 **탐색**인 실행은 판정 근거에서 제외한다.

## 분석 순서

### 1. 이상 점검 먼저

숫자를 비교하기 전에 숫자가 멀쩡한지 본다.

- 자명한 기준선보다 낮은 조건이 있는가 → 설정이 망가졌을 가능성
- 베이스라인이 `survey.md` 의 보고 수치와 크게 다른가 → 평가 설정 차이를 먼저 설명
- seed 간 분산이 조건 간 차이보다 큰가 → 판정 불가 쪽으로 기운다
- 답 추출 실패(빈 예측, 파싱 에러) 비율이 조건마다 다른가 → 이 차이만으로 정확도 차이가 생긴다. 실패율을 따로 보고한다

LLM 평가면 오답 표본 20개 정도를 직접 읽는다. 지표가 잡지 못하는 문제(채점 규칙 오류, 형식만 다른 정답)가 여기서 드러난다.

### 2. 주 비교

`design.md` 의 주 비교 하나에 대해 효과 크기와 신뢰구간을 계산한다.

**같은 평가 항목으로 비교했으면 쌍체 분석을 쓴다.** 항목별 차이를 기준으로 계산하면 항목 난이도의 분산이 상쇄돼서, 같은 N 으로 훨씬 작은 차이를 잡는다.

| 상황 | 방법 |
|---|---|
| 항목별 정오(0/1), 두 조건, 같은 항목 | 쌍체 bootstrap 신뢰구간 + McNemar 검정 |
| 항목별 연속 점수, 두 조건, 같은 항목 | 쌍체 bootstrap 신뢰구간 + Wilcoxon 부호순위 검정 |
| seed 여러 개의 최종 지표 (학습 실험) | seed 별 평균 ± 표준편차, seed 짝이 맞으면 쌍체 t 검정. seed 3개면 검정력이 낮다는 걸 명시 |
| 항목이 다른 두 평가셋 | 독립 bootstrap. 가능하면 설계를 다시 보고 같은 항목으로 맞춘다 |

기본형은 표준 라이브러리만 쓴다. 분석 환경에 numpy·scipy 가 없는 경우가 흔하고, 매번 새로 짜면 구현이 조금씩 달라진다.

```python
import random
from math import comb

def paired_bootstrap_ci(a, b, n_boot=10_000, seed=0, alpha=0.05):
    """a, b: 같은 항목 순서의 항목별 점수. b - a 평균 차이와 (1-alpha) 신뢰구간."""
    diff = [y - x for x, y in zip(a, b)]
    n, rng = len(diff), random.Random(seed)
    boots = sorted(sum(diff[rng.randrange(n)] for _ in range(n)) / n for _ in range(n_boot))
    lo = boots[int(n_boot * alpha / 2)]
    hi = boots[int(n_boot * (1 - alpha / 2)) - 1]
    return sum(diff) / n, (lo, hi)

def mcnemar_exact(b_only, a_only):
    """정확 McNemar 양측 p. b_only: B만 정답 수, a_only: A만 정답 수."""
    n, k = b_only + a_only, min(b_only, a_only)
    if n == 0:
        return 1.0
    return min(1.0, 2 * sum(comb(n, i) for i in range(k + 1)) / 2 ** n)
```

bootstrap 에도 seed 를 고정한다. 분석을 다시 돌려 신뢰구간이 바뀌면 안 된다.

**합계만 있을 때.** 사용자가 조건별 정답 수만 주고 항목별 데이터가 없어도, 같은 항목으로 평가했다면 `B만 정답 − A만 정답` 은 두 합계의 차이로 정해진다. 불일치 쌍이 그 차이만큼만 있는 가장 유리한 경우의 `mcnemar_exact(차이, 0)` 이 p 의 하한이다. 하한이 이미 유의수준을 넘으면 항목별 데이터와 상관없이 "유의하지 않음"이 확정되므로, 데이터를 요청하기 전에 이것부터 계산해 알려준다.

### 3. 판정

`design.md` 의 판정 기준에 결과를 그대로 대입한다.

- **지지** / **기각** / **판정 불가** 중 하나. 기준이 요구한 조건을 인용하고 실제 값을 옆에 쓴다.
- 판정 불가를 "경향이 보인다", "개선 가능성"으로 포장하지 않는다. 판정 불가는 그 자체로 정보다 — 필요한 표본 크기를 추정해 다음 실험으로 넘긴다.
- p-value 만 쓰지 않는다. 효과 크기와 신뢰구간이 주, p-value 는 보조다.

### 4. 보조 비교

- ablation, 보조 지표, 주 비교 외의 조건쌍.
- 비교가 여러 개면 다중 비교 보정(Holm)을 적용하거나, 보정하지 않았다면 **탐색 비교**라고 표시한다.
- 보조 비교에서 나온 흥미로운 패턴은 결론이 아니라 다음 가설이다.

### 5. 대안 설명 점검

`design.md` 의 "대안 설명과 배제 방법"을 하나씩 확인한다. 배제하지 못한 대안 설명은 보고서의 한계에 쓴다.

## 유형별 주의점

### LLM 평가

- **LLM-judge** — A/B 순서를 바꿔 두 번 평가해서 두 판정이 엇갈린 비율(위치 편향)을 보고한다. 엇갈린 항목은 무승부로 처리하거나 제외하고 그 규칙을 적는다.
- **길이 편향** — judge 가 긴 답을 선호하는지 본다. 조건 간 평균 응답 길이를 같이 보고한다.
- **사람 일치도** — 사람 라벨 표본이 있으면 judge 와의 일치도(Cohen's κ 또는 단순 일치율)를 보고한다. 일치도가 낮으면 judge 결과로 판정하지 않는다.
- **자기 선호** — judge 와 평가 대상이 같은 모델 계열이면 그 사실을 한계에 적는다.

### 모델 학습

- 학습 곡선(손실, 검증 지표)을 조건별로 겹쳐 본다. 한 조건만 아직 수렴 중이면 스텝 수가 부족한 것이지 방법이 나쁜 게 아닐 수 있다.
- 최종 지표는 설계에서 정한 체크포인트 기준으로만 보고한다.

### 새 가설 탐색

- 첫 실험 결과는 탐색으로 보고한다. "확증하려면 새 데이터로 무엇을 다시 해야 하는가"를 다음 실험에 적는다.

## `analysis.md` 형식

작업 기록이라 형식이 자유롭지만 다음을 포함한다.

- 사용한 `runs/` 목록과 제외한 실행·제외 이유
- 이상 점검 결과
- 주 비교의 계산 코드 또는 명령, 결과 표
- 판정과 근거
- 보조 비교 결과 (보정 여부 표시)

계산 코드는 `analysis.md` 에 붙이거나 `research/<slug>/analysis.py` 로 저장한다. 같은 `runs/` 에 다시 돌리면 같은 숫자가 나와야 한다.

## `report.md` 쓰기

보고서는 판정의 근거가 된 실제 데이터(`runs/` 또는 사용자가 준 항목별 결과)가 있을 때만 쓴다. 합계만 받았거나 데이터가 오기 전이면 `analysis.md` 까지만 쓰고, 보고서는 데이터를 받은 뒤로 미룬다고 알린다. 추정 시나리오로 채운 보고서는 나중에 결론처럼 인용된다.

`assets/report-template.md` 를 채운다. 규칙:

- **첫 문단이 결론이다.** 가설, 판정, 핵심 수치(효과 크기 + 신뢰구간)를 첫 두 문장에 쓴다. 독자는 이 문단만 읽고 떠날 수 있어야 한다.
- **소제목은 주장이다.** "결과", "분석" 대신 "CoT 는 7B 에서 +4.1%p, 1B 에서는 차이 없음"처럼. 소제목만 훑어도 보고서를 이해할 수 있게.
- **모든 수치는 `runs/` 나 `analysis.md` 에서 나온다.** 수치 옆에 어느 run 또는 분석에서 나왔는지 추적할 수 있게 한다.
- **한계를 숨기지 않는다.** 배제하지 못한 대안 설명, 작은 seed 수, 오염 가능성, 탐색 비교.
- **다음 실험은 구체적으로.** "추가 연구 필요"가 아니라 무엇을, 왜, 어떤 설계로.
- 헤지("~일 수도 있다")는 실제로 불확실한 곳에만 쓰고, 불확실한 이유를 같이 쓴다.
