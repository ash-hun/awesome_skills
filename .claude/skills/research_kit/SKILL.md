# research_kit: 가설 하나를 실험으로 검증하는 키트

실험은 결과보다 **결과를 믿을 수 있는 근거**가 더 중요하다. 같은 코드를 다시 돌려 같은 숫자가 나오는가, 비교한 두 조건이 정말 한 가지만 달랐는가, 평가 기준이 결과를 보기 전에 정해져 있었는가. 이걸 답하지 못하는 실험 결과는 숫자일 뿐 근거가 아니다. 이 키트는 가설 하나를 받아 다섯 단계를 거치며 그 근거를 쌓고, 마지막에 "이 결과를 본 연구에 쓸 수 있는가"에 답한다.

```
가설(입력)  →  1. 조사  →  2. 설계  →  3. 검증  →  4. 평가  →  5. 판단  →  보고서
               survey      design      verification  evaluation  decision    report
```

가설 수립은 이 키트의 범위가 아니다. 가설은 연구 주제에서 나오고 사용자가 가져온다. 키트는 그 가설이 맞는지 실험으로 확인하고, 확인한 결과를 본 연구에 넣을지 판단한다.

## 단계 고르기

사용자가 어디에 있는지 먼저 파악하고 그 단계부터 시작한다. 이미 결과 표를 가져왔는데 조사부터 하자고 하면 시간만 버린다. 단, **앞 단계의 산출물이 비어 있으면 그 사실을 알린다.** 설계 문서 없이 결과를 평가하면 평가 기준이 결과를 본 뒤에 만들어진다.

| 사용자의 상태 | 시작 단계 | 읽을 참조 |
|---|---|---|
| 가설은 있고 관련 연구를 모름 | 1 조사 | `references/survey.md` |
| 가설과 관련 연구를 알고 실험을 짜야 함 | 2 설계 | `references/design.md` |
| 설계가 있고 돌릴 준비가 됨 | 3 검증 | `references/verification.md` |
| 실행 결과가 있고 채점해야 함 | 4 평가 | `references/evaluation.md` |
| 평가가 끝났고 쓸지 정해야 함, 또는 보고서 | 5 판단 | `references/decision.md` |

참조 문서는 **그 단계에 들어갈 때 읽는다.** 다섯을 미리 다 읽지 않는다.

가설이 없는 사용자(주제만 있음)는 먼저 `assets/hypothesis-template.md` 를 같이 채운다. 한 문장이면 된다. 가설 없이 조사를 시작하면 조사가 끝없이 넓어진다.

1단계 조사는 깊이가 둘이다. 일반 실험이면 **light**(직접 검색 몇 번으로 베이스라인, 평가셋, 함정, 반박 근거만 확인), 실제 논문을 쓰는 경우에만 **full**(조사 서브에이전트를 병렬로 띄우는 문헌 조사). 기준과 절차는 `references/survey.md` 의 "깊이 고르기"에 있다.

## 연구 폴더

연구 하나의 산출물은 한 폴더에 모은다. 대화가 끊겨도 다음 세션이 이 폴더만 보고 이어갈 수 있게 하기 위해서다. 연구 하나 아래 실험이 여러 개 달리고, 보고서는 연구 단위로 하나다.

```
research/<slug>/
├── hypothesis.md              # 입력. 연구 주제, 가설, 본 연구에서 이 실험이 맡는 역할
├── survey.md                  # 1단계. 지지와 반박 근거, 가져다 쓸 자원, 동향, 방향 제안
├── notes/                     # 1단계 full 에서만. 조사 서브에이전트의 원자료 노트
├── design.md                  # 2단계. 실험 목록, 변인 통제, 평가 기준, seed, 예산
├── experiments/<exp-id>/      # 3단계. 실험 하나당 폴더 하나
│   ├── run.py 또는 run.ipynb  #   실험 코드 (assets/run_template.py)
│   ├── runs/<run-id>/         #   실행 하나당 폴더 하나
│   │   ├── card.md            #     실행 카드 (assets/experiment-card.md)
│   │   ├── config.*           #     실제로 쓴 설정 파일 사본
│   │   └── metrics.jsonl      #     항목 단위 원 지표
│   └── figures/               #   보고서에 들어갈 그림
├── evaluation.md              # 4단계. 기준 적용 결과, 이상 점검, 미충족 확인 기록
├── decision.md                # 5단계. 채택 여부와 근거, 다음 행동
└── report.md                  # 보고서 (assets/report-template.md)
```

- `<slug>` 와 `<exp-id>` 는 영어 소문자와 하이픈(`cot-vs-direct-gsm8k`, `exp1-model-sweep`). 저장소 루트에 `research/` 가 없으면 만든다. 사용자가 다른 위치를 쓰고 있으면 그쪽을 따른다.
- 폴더가 이미 있으면 새로 만들지 않고 이어서 쓴다. 각 단계는 **자기 파일만** 덮어쓴다. 같은 단계를 두 번 돌려도 다른 단계의 파일은 바뀌지 않는다.
- `runs/` 는 추가만 한다. 실패한 실행도 지우지 않고 카드에 실패로 기록한다. 지운 실패는 나중에 "왜 이 설정은 안 썼지?"에 답하지 못하게 만든다.

## 원칙

여덟 가지. 각 단계 참조 문서가 이 원칙을 구체화한다.

1. **평가 기준을 먼저 적는다.** 무엇을 어떤 형식으로 재고, 몇 이상이면 통과인지를 실행 전에 `design.md` 에 쓴다. 결과를 본 뒤에 기준을 정하면 어떤 결과든 통과한다. 실행 뒤에 설계를 바꿔야 하면 원문을 지우지 않고 `## 변경 이력` 에 날짜와 이유를 남긴다.
2. **기준은 믿을 만해야 한다.** 평가는 신뢰할 수 있고 흠 없는 기준으로 판단을 내리는 일이고, 그래서 평가 결과가 성능을 대변한다. 기준마다 "이 기준이 믿을 만한 이유"를 한 줄 적는다(표준 벤치마크의 채점 규칙 그대로, 사람 라벨과 일치율 확인, 결정적 규칙이라 재채점이 같음 등). 이유를 못 쓰는 기준은 쓰지 않는다.
3. **기준이 정확히 충족되지 않으면 멈추고 묻는다.** 채점 규칙에 안 맞는 항목, 추출 실패, judge 일치도 미달, 평가셋 버전 불일치처럼 기준을 그대로 적용할 수 없는 상황이 나오면 임의로 처리하지 않는다. 사용자에게 확인하고 결정을 `evaluation.md` 에 남긴다.
4. **베이스라인부터 돌린다.** 제안 방법보다 비교 대상을 먼저 재현한다. 베이스라인이 문헌 수치를 재현하지 못하면, 그 차이부터 설명해야 제안 방법의 결과를 해석할 수 있다.
5. **한 번에 한 변수.** 두 조건의 차이는 검증하려는 변수 하나여야 한다. 프롬프트와 temperature 를 같이 바꾸면 무엇이 효과를 냈는지 알 수 없다. 실험마다 "무엇을 고정하고 무엇만 바꿨는지"를 표로 적는다.
6. **실행 카드 없는 결과는 결과가 아니다.** 모든 실행은 `card.md` 에 config, git commit, seed, 환경, 데이터 버전, 실행 명령을 남긴다. 카드를 채울 수 없는 실행(커밋 안 된 코드, 기록 안 된 seed)은 탐색으로만 쓰고 보고서의 근거로 쓰지 않는다.
7. **숫자를 지어내지 않는다.** 보고서의 모든 수치는 `runs/` 의 원 지표나 출처가 있는 문헌에서 나온다. 실행하지 않은 실험의 예상 수치를 결과처럼 쓰지 않는다.
8. **seed 분산을 같이 보고한다.** seed 를 여러 개 돌렸으면 평균 옆에 표준편차와 항목 수를 적는다. 조건 간 차이가 seed 간 차이보다 작으면 "차이 있음"이라고 쓰지 않는다.

## 실험 유형

같은 다섯 단계를 거치지만, 유형마다 설계와 평가에서 주의할 점이 다르다. `design.md` 와 `evaluation.md` 참조 문서에 유형별 절이 있다.

- **LLM 평가**: 모델이나 프롬프트의 성능을 벤치마크나 자체 평가셋으로 측정. 오염(contamination), LLM-judge 편향, 디코딩 설정 고정이 핵심.
- **비교대조 실험**: 두 개 이상의 조건(A/B, 방법 간)을 같은 평가셋에서 비교. 같은 항목으로 평가하는 것과 주 비교를 하나로 정하는 것이 핵심.
- **모델 학습과 파인튜닝**: 학습 설정을 바꿔 결과 모델을 비교. seed 분산, 체크포인트 선택 기준, 계산 예산 동등성이 핵심.
- **새 가설 탐색**: 아직 선행 연구가 적은 현상을 검증. 반증 가능한 형태로 가설을 쓰는 것과 대조 조건 설계가 핵심.

## 단계 사이를 잇기

각 단계가 끝나면 다음 단계를 **제안한다**. 사용자가 "설계는 됐고 평가만 해줘"라고 하면 따른다.

- 1 → 2: `survey.md` 끝의 방향 제안(가설 유지, 수정, 범위 조정)을 AskUserQuestion 으로 고르게 하고 설계로
- 2 → 3: 설계의 평가 기준과 임계값이 채워졌는지 확인하고 검증으로. 비었으면 채우자고 먼저 말한다
- 3 → 4: 계획한 실행이 다 끝났는지 `experiments/*/runs/` 를 보고 확인. 빠진 조건이 있으면 알린다
- 4 → 5: 기준 미충족으로 보류된 항목이 남아 있으면 판단으로 넘어가지 않는다
- 5 → 보고서: 판단이 끝나면 `report.md` 를 쓴다. 판단이 "판정 불가"면 보고서의 결론에 그렇게 쓰고, 다음 실험을 적는다
- 5 → 2 또는 1: 기각이나 판정 불가에서 나온 다음 실험이 같은 가설이면 2단계로, 가설을 고쳐야 하면 `hypothesis.md` 를 고치고 1단계로

## 사용자와 대화할 때

결정이 필요한 질문(어느 벤치마크를 쓸지, 계산 예산이 얼마인지, 노트북과 모듈 중 무엇으로 할지, 기준 미충족 항목을 어떻게 처리할지)은 AskUserQuestion 으로 묻는다. 찾아볼 수 있는 사실(저장소에 이미 있는 평가 스크립트, 설치된 라이브러리 버전, GPU 종류)은 묻지 않고 직접 확인한다.

## 범위 밖

- 가설 수립. 연구 주제에서 가설을 끌어내는 일은 사용자 몫이다. 가설 문장을 반증 가능한 형태로 다듬는 것까지만 돕는다.
- 연구와 무관한 웹 조사나 시장 조사.
- 실험 결과를 논문 원고 형식(LaTeX, 투고 양식)으로 쓰는 일. 보고서까지만 다룬다.
- 학습 인프라 구축(클러스터, 스케줄러, 분산 학습 설정). 검증 단계는 이미 돌릴 수 있는 환경을 전제로 한다.
- 통계 검정. 효과를 가설 검정으로 판정하지 않는다. 기준 충족 여부와 seed 분산 표기로 판단한다.

## 크레딧

1단계 full 조사 절차(조정자와 서브에이전트 분업, 노트 형식, 출처 평가, 요약 문단과 주장형 소제목)는 Anthropic 의 `deep-research` 스킬에서 유효한 부분을 골라 연구 문헌 조사에 맞게 다시 쓴 것이다.
