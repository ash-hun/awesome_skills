# research_kit — AI 연구·실험 키트

실험은 결과보다 **결과를 믿을 수 있는 근거**가 더 중요하다. 같은 코드를 다시 돌려 같은 숫자가 나오는가, 비교한 두 조건이 정말 한 가지만 달랐는가, 그 차이가 seed 운인지 실제인지 — 이걸 답하지 못하는 실험 결과는 숫자일 뿐 발견이 아니다. 이 키트는 네 단계를 거치며 그 근거를 쌓는다.

```
1. 질문·선행 조사  →  2. 가설·실험 설계  →  3. 실행·로깅  →  4. 분석·보고서
     survey              design               execution          analysis
```

## 단계 고르기

사용자가 어디에 있는지 먼저 파악하고 그 단계부터 시작한다. 이미 결과 표를 가져왔는데 선행 조사부터 하자고 하면 시간만 버린다. 단, **앞 단계의 산출물이 비어 있으면 그 사실을 알린다** — 설계 문서 없이 결과를 분석하면 "무엇을 기대했는가"가 사후에 만들어진다.

| 사용자의 상태 | 시작 단계 | 읽을 참조 |
|---|---|---|
| 주제만 있음, 무엇을 검증할지 모름 | 1 | `references/survey.md` |
| 가설이나 비교할 조건이 있음 | 2 | `references/design.md` |
| 설계가 있고 돌릴 준비가 됨 | 3 | `references/execution.md` |
| 결과·로그가 있음 | 4 | `references/analysis.md` |

참조 문서는 **그 단계에 들어갈 때 읽는다.** 넷을 미리 다 읽지 않는다.

1단계 조사는 깊이가 둘이다. 일반 연구·실험·결과 도출이면 **light**(직접 검색 몇 번으로 베이스라인·평가셋·함정만 확인), 실제 논문을 쓰는 경우에만 **full**(조사 서브에이전트를 병렬로 띄우는 문헌 조사). 기준과 절차는 `references/survey.md` 의 "깊이 고르기"에 있다.

## 연구 폴더

한 연구 주제의 산출물은 한 폴더에 모은다. 대화가 끊겨도 다음 세션이 이 폴더만 보고 이어갈 수 있게 하기 위해서다.

```
research/<slug>/
├── survey.md          # 1단계 — 선행 조사 종합, 연구 질문 후보
├── notes/             # 1단계 full — 조사 서브에이전트의 원자료 노트
├── design.md          # 2단계 — 가설·변인·지표·판정 기준 (assets/design-template.md)
├── runs/<run-id>/     # 3단계 — 실행 하나당 폴더 하나
│   ├── card.md        #   실험 카드 (assets/experiment-card.md)
│   ├── config.*       #   실제로 쓴 설정 파일 사본
│   └── metrics.*      #   원 지표 (jsonl/csv)
├── analysis.md        # 4단계 — 비교·통계·판정
└── report.md          # 4단계 — 보고서 (assets/report-template.md)
```

- `<slug>` 는 영어 소문자·하이픈(`cot-vs-direct-gsm8k`). 저장소 루트에 `research/` 가 없으면 만든다. 사용자가 다른 위치를 쓰고 있으면 그쪽을 따른다.
- 폴더가 이미 있으면 새로 만들지 않고 이어서 쓴다. 각 단계는 **자기 파일만** 덮어쓴다 — 같은 단계를 두 번 돌려도 다른 단계의 파일은 바뀌지 않는다.
- `runs/` 는 추가만 한다. 실패한 실행도 지우지 않고 카드에 실패로 기록한다. 지운 실패는 나중에 "왜 이 설정은 안 썼지?"에 답하지 못하게 만든다.

## 원칙

일곱 가지. 각 단계 참조 문서가 이 원칙을 구체화한다.

1. **판정 기준을 먼저 적는다.** 가설, 주 지표, "몇 이상이면 지지"를 실행 전에 `design.md` 에 쓴다. 결과를 본 뒤에 기준을 정하면 어떤 결과든 성공으로 읽을 수 있다. 실행 뒤에 설계를 바꿔야 하면 원문을 지우지 않고 `## 변경 이력` 에 날짜와 이유를 남긴다.
2. **베이스라인부터 돌린다.** 제안 방법보다 비교 대상을 먼저 재현한다. 베이스라인이 논문 수치를 재현하지 못하면, 그 차이부터 설명해야 제안 방법의 결과를 해석할 수 있다.
3. **한 번에 한 변수.** 두 조건의 차이는 검증하려는 변수 하나여야 한다. 프롬프트와 temperature 를 같이 바꾸면 무엇이 효과를 냈는지 알 수 없다.
4. **실험 카드 없는 결과는 결과가 아니다.** 모든 실행은 `card.md` 에 config, git commit, seed, 환경, 데이터 버전, 실행 명령을 남긴다. 카드를 채울 수 없는 실행(커밋 안 된 코드, 기록 안 된 seed)은 탐색으로만 쓰고 보고서의 근거로 쓰지 않는다.
5. **숫자를 지어내지 않는다.** 보고서의 모든 수치는 `runs/` 의 원 지표나 출처가 있는 문헌에서 나온다. 실행하지 않은 실험의 예상 수치를 결과처럼 쓰지 않는다.
6. **불확실성을 같이 보고한다.** 평균만 쓰지 않는다. seed 여러 개의 표준편차, 또는 표본 기반 신뢰구간을 붙인다. 차이가 구간 안에 있으면 "차이 없음"이 아니라 "판정 불가"로 쓴다.
7. **작게 먼저.** 전체 실행 전에 데이터 몇 개, 스텝 몇 개로 끝까지 한 번 돈다. 비싼 실행이 마지막 저장 단계에서 죽는 걸 막는다.

## 실험 유형

같은 네 단계를 거치지만, 유형마다 설계와 분석에서 주의할 점이 다르다. `design.md` 와 `analysis.md` 참조 문서에 유형별 절이 있다.

- **LLM 평가** — 모델·프롬프트의 성능을 벤치마크나 자체 평가셋으로 측정. 오염(contamination), LLM-judge 편향, 디코딩 설정 고정이 핵심.
- **비교대조 실험** — 두 개 이상의 조건(A/B, 방법 간)을 같은 평가셋에서 비교. 쌍체(paired) 비교와 다중 비교 보정이 핵심.
- **모델 학습·파인튜닝** — 학습 설정을 바꿔 결과 모델을 비교. seed 분산, 체크포인트 선택 기준, 계산 예산 동등성이 핵심.
- **새 가설 탐색** — 아직 선행 연구가 적은 현상을 검증. 반증 가능한 형태로 가설을 쓰는 것과 대조 조건 설계가 핵심.

## 단계 사이를 잇기

각 단계가 끝나면 다음 단계를 **제안한다**. 사용자가 "설계는 됐고 분석만 해줘"라고 하면 따른다.

- 1 → 2: `survey.md` 끝의 연구 질문 후보 중 하나를 AskUserQuestion 으로 고르게 하고 설계로
- 2 → 3: 설계의 판정 기준이 채워졌는지 확인하고 실행으로. 비었으면 채우자고 먼저 말한다
- 3 → 4: 계획한 실행이 다 끝났는지 `runs/` 를 보고 확인. 빠진 조건이 있으면 알린다
- 4 → 1 또는 2: 분석에서 나온 "다음 실험"이 새 가설이면 2단계로, 새 질문이면 1단계로

## 사용자와 대화할 때

결정이 필요한 질문(어느 벤치마크를 쓸지, 계산 예산이 얼마인지, 어떤 가설을 먼저 볼지)은 AskUserQuestion 으로 묻는다. 찾아볼 수 있는 사실(저장소에 이미 있는 평가 스크립트, 설치된 라이브러리 버전, GPU 종류)은 묻지 않고 직접 확인한다.

## 범위 밖

- 연구와 무관한 웹·시장 조사. 그건 조사 보고서 전용 스킬의 몫이다.
- 실험 결과를 논문 원고 형식(LaTeX, 투고 양식)으로 쓰는 일. 보고서까지만 다룬다.
- 학습 인프라 구축(클러스터, 스케줄러, 분산 학습 설정). 실행 단계는 이미 돌릴 수 있는 환경을 전제로 한다.

## 크레딧

1단계 full 조사 절차(조정자·서브에이전트 분업, 노트 형식, 출처 평가, 요약 문단과 주장형 소제목)는 Anthropic 의 `deep-research` 스킬에서 유효한 부분을 골라 연구 문헌 조사에 맞게 다시 쓴 것이다.
